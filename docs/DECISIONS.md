# 의사결정 기록 (DECISIONS)

> 한 결정당 5줄 내외. README의 "UI/UX 설계 판단"·"설계 의도"와 서술형 문항은 이 파일에서 조립한다.

## D-001 주제: 독서모임 기록 서비스 (2026-07-25)

- 선택지: 개인 독서 노트(안내문 예시) / 육아일기 / 독서모임 기록
- 결정: 독서모임 기록 + 모임 문집 제작
- 이유: ① 안내문 예시(개인 독서노트)와 차별화 ② 실제 관찰에서 나온 기획 근거(독서모임 지인들의 기록이 대화방에 흩어져 사라짐) ③ 모임 단위 주문은 "멤버 수만큼 N부"라는 자연스러운 주문 동기가 있어 인쇄 API 수요처로서 설득력 큼
- 연결: 서술형 문항 1(기획 의도), README §7

## D-002 모노레포 + docker-compose 단일 실행 (2026-07-25)

- 선택지: 프론트/백 레포 분리 vs 모노레포
- 결정: 모노레포 (frontend/ + backend/ + 루트 docker-compose.yml)
- 이유: "docker-compose up 1회 실행" 요건. 심사자가 clone 한 번, 명령 한 번으로 끝나야 함
- 연결: 제출 요건 체크리스트

## D-003 로그인 대신 '프로필 선택 입장' (2026-07-25, 개정)

- 선택지: 이메일/비밀번호 로그인 / 완전 무인증 단일 사용자 / 프로필 선택 입장
- 결정: 첫 화면에서 모임 멤버 프로필을 선택해 입장. 선택한 멤버가 이후 세션의 기준(코멘트 작성자·마이페이지)
- 이유: 안내문 "회원 인증은 구현 대상 아님" + "실행 직후 로그인 없이 바로 확인" 요건. 모임 서비스의 핵심인 '누구의 코멘트인지'와 멤버 관점 화면(마이페이지)은 유지하면서 인증 비용만 제거. 제품 비전의 가입/로그인은 README '의도적으로 넣지 않은 것'에 근거와 함께 기록
- 연결: Lv3 첫 진입 이해, README §4

## D-006 런타임 AI 기능 미탑재 (2026-07-25)

- 선택지: AI 요약/추천 기능 탑재 vs 미탑재
- 결정: 서비스 런타임에는 AI 미탑재. AI는 개발 과정(코드 생성·더미데이터·QA)에서 활용하고 AI_LOG에 기록

- 이유: 온라인 모임(오픈채팅) 관찰 결과 실제 가치는 '기록 보관'보다 '토론이 책 단위로 쌓이는 것'. 페이지·인용 앵커가 있는 스레드는 문집의 콘텐츠 밀도도 높임
- 연결: PLAN §3~5, 서술형 문항 1·2

## D-009 주문 상태 8단계 구체화 (2026-07-25)

- 선택지: 3단계(pending/processing/completed — 안내문 예시 수준) / 실물 제작 라이프사이클 8단계
- 결정: 접수 → 확인 → 제작 → 제작완료 → 배송시작 → 배송중 → 배송완료 → 구매확정. 단계 진행은 관리자, 구매 확정은 주문자만. 모든 전이는 날짜와 함께 이력 기록
- 이유: 실물 책 제작 서비스의 실제 주문 흐름을 반영해 "지금 어디쯤인지"를 구체적으로 전달. 배송 자체는 구현하지 않고 상태·이력으로만 표현(안내문 제외 범위 준수)
- 연결: PLAN §5, QA "Lv2 로직 검증", 서술형 문항 2
- **개정**: [[D-034]]에서 '배송중'(`IN_TRANSIT`)을 삭제해 **7단계**가 됐다 — 제작처는 `SHIPPED → DELIVERED`뿐이라 대응하는 이벤트가 없었다

## D-011 모노레포 구조·Docker 실행 방식 (2026-07-26)

- 선택지: npm 워크스페이스 모노레포 / 워크스페이스 없이 frontend·backend 폴더 분리 · dev 서버 컨테이너 / 프로덕션 빌드 컨테이너
- 결정: 폴더 분리(각자 독립 package.json) + 멀티스테이지 프로덕션 빌드(Next standalone, Nest dist). 포트·DB 접속정보는 compose에서 환경변수 기본값(`${VAR:-기본}`)으로 처리
- 이유: 워크스페이스 호이스팅은 Docker 빌드 컨텍스트를 복잡하게 만듦 — 앱 2개 규모에선 이득이 없음. 심사자는 `docker-compose up` 1회 실행이 요건이므로 dev 서버가 아닌 프로덕션 빌드가 안정적. NEXT*PUBLIC*\*는 빌드 타임에 번들에 박히므로 빌드 아규먼트로 주입
- 연결: PLAN §9·§10, TODO 인프라 항목

## D-012 시드·마이그레이션 실행 전략 (2026-07-26)

- 선택지: 시드를 README 수동 명령으로 안내 / 컨테이너 기동 시 자동 실행 · 시드를 TS(ts-node 필요) / 순수 JS
- 결정: backend 컨테이너 CMD에서 `prisma migrate deploy → node prisma/seed.js → 앱 시작` 순서로 자동 실행. 시드는 순수 JS로 작성하고 데이터가 있으면 스킵(멱등). prisma CLI는 런타임에 필요하므로 prod 의존성으로 설치, 메이저는 6으로 고정(7의 새 설정 체계 학습 비용 회피)
- 이유: 안내문 요건이 "docker-compose up 1회 → 더미데이터로 즉시 탐색". 수동 단계가 하나라도 있으면 실패 지점이 됨. ts-node를 프로덕션 이미지에 넣는 것보다 JS 시드가 가벼움
- 연결: PLAN §10 (Docker 1회 실행 + 더미데이터), TODO 인프라 항목

## D-013 주문 상태 확장: 취소·환불·재제작 분기 (2026-07-26, D-009 확장)

- 선택지: 순방향 8단계 유지 / 취소만 / 취소·환불·교환 / 취소·환불·재제작
- 결정: 순방향 8단계 + CANCELED(접수·확인에서만, 주문자·관리자), REFUND_REQUESTED(배송완료에서, 주문자)→REFUNDED(관리자), REMAKE_REQUESTED(배송완료에서, 주문자)→승인 시 IN_PRODUCTION 재진입(관리자). 종결: 구매확정·취소·환불완료. 단순 변심 환불·교환은 없음 — 배송 후 하자 시에만 환불 또는 재제작
- 이유: 과제사 스위트북은 주문제작(POD) 인쇄 서비스 — 전자상거래법 §17 청약철회 제한 대상이라 "제작 전 취소 / 하자 시 재제작 또는 환불"이 업계 구조. POD에는 재고가 없어 '교환' 개념이 성립하지 않고 구제책은 '재제작'. 분기 덕에 전이 맵 검증·권한 테스트가 풍부해져 Lv2 평가 포인트도 강화
- 연결: PLAN §5 전이 맵, CLAUDE.md 컨벤션, QA "Lv2 로직 검증", 서술형 문항 1·2, README 설계 의도

## D-014 식별자 전략: int PK + publicId(cuid) 노출 (2026-07-26)

- 선택지: int id 그대로 노출 / PK를 UUID로 교체 / int PK 유지 + publicId 별도 추가
- 결정: 노출 모델(Member·Club·Book·Comment·Order)에 publicId(cuid, unique) 추가. API 경로·응답은 publicId만, 내부 PK·FK는 자동증가 int 유지
- 이유: 순번 노출은 규모 추정·URL 열거를 허용 — 외부 식별자 분리는 실무 관행. int FK를 유지해 조인 성능·디버깅 편의는 그대로
- 연결: PLAN §5, CLAUDE.md 컨벤션

## D-015 회원-모임 다대다 재구조화 (2026-07-26)

- 선택지: Member가 클럽 소속(1:N) / Member 전역 + ClubMember(가입) 다대다
- 결정: Member는 전역 회원, 소속·역할·가입일은 ClubMember(clubId, memberId, role, joinedAt)로 관리. UI·데모는 §7 비목표대로 시드 모임 1개 유지
- 이유: 개인이 여러 모임에 가입하는 제품 비전(로드맵 커뮤니티·모임 찾기)과 정합. 마이그레이션을 새로 만드는 지금이 구조 변경 비용이 가장 싼 시점
- 연결: PLAN §5·§7·§8, 서술형 문항 1

## D-016 문서 배치 기준 + 컨벤션 문서 최소주의 (2026-07-26)

- 선택지: 모든 문서를 루트 docs/에 집중 / 앱별 docs/로 전부 분산 / 적용 범위 기준 하이브리드 · 스키마 컨벤션 문서 작성 여부
- 결정: 프/백 공통·기획·프로세스는 루트 docs/, 한쪽 앱에만 해당하는 문서는 그 앱의 docs/. 단 지엽적 컨벤션 문서(스키마 컨벤션 등)는 만들지 않음 — 기존 코드·파일이 컨벤션의 기준이며, 새 파일은 기존 패턴을 따라 생성
- 이유: 컨벤션 수정은 해당 앱 코드와 같은 커밋에서 일어나므로 근접성이 중요하고, 레포 분리 시 문서가 앱을 따라감. 문서가 잘게 늘어나면 유지비만 증가 — "코드가 곧 문서" 원칙으로 절제
- 연결: CLAUDE.md 컨벤션

## D-017 API 표면 설계: publicId 라우팅 + X-Member-Id 멤버 컨텍스트 (2026-07-26)

- 선택지: 멤버 식별을 요청 바디마다 포함 / 쿼리 파라미터 / 커스텀 헤더(X-Member-Id)
- 결정: 모든 API는 `/api` 프리픽스 + publicId 라우팅(D-014). 쓰기 요청의 현재 멤버는 `X-Member-Id` 헤더(프로필 선택 시 저장한 publicId)로 식별. 권한은 서버에서 검증 — 책 등록·수정·삭제는 모임장(LEADER)만, 코멘트 수정·삭제는 작성자만, 코멘트 작성은 모임 멤버만
- 이유: 인증 미구현(D-003)이어도 '누구의 행동인지'는 서버가 검증해야 Lv2 권한 로직과 일관됨. 헤더 방식은 바디 오염 없이 모든 메서드(DELETE 포함)에 균일 적용. 답글 1단계 제한·삭제된 코멘트에 답글 금지 등 스레드 규칙도 서버 검증
- 연결: PLAN §3 F1·F2, D-003·D-014, QA "Lv2 로직 검증"

## D-018 API 에러 표준화: 전역 필터 + 메시지 enum (2026-07-26)

- 선택지: Nest 기본 에러 응답 그대로(검증은 배열·도메인은 문자열로 불일치) / 전역 예외 필터로 포맷 통일
- 결정: 전역 필터가 모든 에러를 `{ statusCode, messages: string[], timestamp, path }`로 통일. 사용자 노출 메시지는 `shared/constants/error-message.ts`의 ErrorMessage enum을 단일 소스로 삼아 도메인 예외와 DTO 검증 메시지가 공유. 예상 못한 500은 스택을 서버 로그로 남기고 일반 메시지만 노출
- 이유: 프론트 에러 처리(Lv3 루브릭 '입력 검증 메시지·실패 화면')가 한 가지 포맷만 다루면 됨. 메시지가 코드 곳곳에 흩어지면 문구 수정·톤 통일이 어려움
- 연결: CLAUDE.md 컨벤션, QA 루브릭 ③, Lv3

## D-028 에러 계약을 코드(enum) 기반으로 전환 (2026-07-29)

- 선택지: 한글 메시지 문자열이 계약(기존 D-018) / 에러 타입 enum이 계약이고 메시지는 부속
- 결정: `shared/constants/error-code.ts`의 **ErrorCode enum이 API 에러 계약**. 서비스 예외·DTO 검증 모두 코드를 던지고, 전역 필터가 코드별 기본 한글 메시지(ERROR_MESSAGE 맵 — 카피 단일 소스)를 붙여 `{ statusCode, errors: [{ code, message }], timestamp, path }`로 응답. 프론트는 **code로 분기**(예: 세션 무효 = MEMBER_NOT_FOUND·MEMBER_HEADER_REQUIRED → 자동 로그아웃)하고 **표시는 서버 message를 그대로** 사용 — 프론트에 별도 한글 맵을 두지 않아 카피 이원화를 막는다. 검증 상세는 `CODE|상세` 규약으로 필터에서 괄호 표기(UNKNOWN_FIELD 등)
- 이유: 문자열 매칭 분기는 카피 수정만으로 로직이 깨지는 취약 구조(실제로 axiosClient가 한글 문자열을 비교하고 있었음). 코드가 계약이면 FE/BE가 안전하게 분기하고, 카피는 서버 한 곳에서만 관리된다. 다국어·에러 트래킹 확장에도 코드가 기준이 됨
- 보강(2026-07-29): 에러 응답 스키마(ApiErrorResponse + ErrorCode enum)를 OpenAPI에 실어 프론트가 생성 타입으로 코드 분기하도록 했다 — 계약을 선언만 하고 스펙에 싣지 않으면 프론트가 문자열을 손으로 재선언하게 되어 D-020(codegen) 취지와 어긋난다. 검증 실패의 필드명은 `CODE|$property` 규약으로 함께 전달
- 연결: D-018(카피 단일 소스 — 유지, 위치가 ERROR_MESSAGE 맵으로 이동), D-020(codegen), axiosClient 세션 무효 판정

## D-029 어드민 진입: 로그인 모달의 '관리자' 탭 + 배타적 세션 (2026-07-29)

- 선택지: 별도 어드민 웹 프로젝트 분리 / 한 프로젝트에서 URL(/admin)만 분리 / 로그인 모달에 관리자 탭 + 전용 셸
- 결정: **한 프로젝트 안에서 로그인 모달을 회원·관리자 탭으로 나누고**, 관리자로 들어가면 운영자 전용 GNB(주문 관리·회원 관리)와 `/admin/*` 화면으로 전환한다. 세션은 회원과 관리자가 **상호 배타** — 관리자 세션은 서비스 화면에, 회원 세션은 어드민 화면에 접근할 수 없다. 서버는 기존대로 `/admin/*` 경로로만 분리(D-003·D-022)하고 인증은 넣지 않는다
- 이유: 실서비스라면 어드민은 별도 앱·별도 인증이지만, 과제는 "실행 직후 바로 확인"이 요건이라 진입점이 숨으면 안 된다. 로그인에 통합하면 심사자가 헤매지 않고, 화면 전환으로 '서비스와 운영자는 다른 세계'라는 판단도 드러난다. 인증이 목이라는 사실은 모달 문구와 README에 명시해 과장하지 않는다

## D-030 회원·클럽은 조회 + 운영자 메모까지만 (2026-07-29, 2026-07-31 개정)

- 최초 결정: `Member.status`(ACTIVE·SUSPENDED)를 두고 운영자가 정지·해제하며, 정지 회원은 로그인·쓰기가 서버에서 차단되게 한다
- **개정 결정: 상태 전환을 만들지 않는다.** 회원·클럽은 **조회 전용**이고, 운영자가 남길 수 있는 것은 **운영자 메모**(`Member.adminNote`·`Club.adminNote`)뿐이다
- 개정 이유: 이 서비스의 비즈니스 로직은 **문집 주문 한 축**에 모으는 편이 설명하기 쉽다.
- 메모를 남긴 이유: 조회만 하는 화면이라도 운영자에게는 **응대 이력**이 필요하다. 다음 담당자가 같은 문의를 처음부터 다시 파악하지 않도록 하는 최소 장치이고, 주문 이력의 '운영자 메모'(D-031)와 같은 문법이다
- 화면 구성: 주문 관리 / 회원 관리 / 클럽 관리 세 메뉴. 회원·클럽 모두 목록 → 상세이고, 상세에서 서로를 오간다([[D-037]])
- 회원 목록의 좁히기는 **드롭다운이 아니라 검색**이다 — 이름·회원 ID·클럽명을 한 필드에서 찾는다. 클럽이 늘어날수록 드롭다운은 감당이 안 되고, 운영자가 찾는 방식은 대개 "이름 일부를 기억하는" 쪽이다. 클럽 단위 좁히기는 클럽 상세의 '이 클럽 회원 목록'이 URL 쿼리(`?clubId=`)로 걸어 주고, 화면에는 지울 수 있는 칩으로 보인다
- 연결: [[D-031]](운영자 메모), [[D-037]](상세를 페이지로)

## D-033 북프린트 API 파트너사로 재정합 (2026-07-30)

- 선택지: 자체 상상 사양으로 두기 / 공개 문서(`api.sweetbook.com/docs/llms-full.txt`) 기준으로 주문 도메인을 맞추기
- 결정: **문서 그대로 맞춘다.** 제작 방식은 `PDF_UPLOAD` 하나로 고정, 표준 판형 3종(`PHOTOBOOK_A5_SC`·`PHOTOBOOK_A4_SC`·`SQUAREBOOK_HC`)만 카탈로그로 노출, 페이지 규칙(`pageMin`/`pageMax`/`pageIncrement=2`)·가격 공식·SLA(제작 3~4영업일 + 배송 1~2일)를 그대로 재현. 실제 호출은 하지 않고 `shared/bookprint/` 목 클라이언트가 벤더 계약(6필드 응답·`ERR_*` 코드)을 재현
- 이유: 과제가 보는 것은 **콘텐츠 서비스를 어떻게 기획하고 최종 사용자를 고려해 설계했는가**다. 안내문도 "서비스의 주인공은 콘텐츠이고 책 만들기는 그 위의 부가 기능"이라고 못박는다 — 그 우선순위는 그대로 지킨다. 다만 합류 후 실제로 맡게 될 일은 **인쇄 API 플랫폼 자체**이므로, 이 과제를 **그 API를 쓰게 될 파트너사를 직접 만들어 보는 기회**로 삼았다. 파트너 입장에서 문서를 읽고 제약(판형에 묶인 사양·페이지 규칙·취소 가능 구간·웹훅으로만 오는 상태)을 실제로 받아 보면, 이 API가 어떤 서비스에서 어떻게 쓰이는지와 연동하는 쪽이 무엇을 신경 써야 하는지를 미리 이해할 수 있다고 봤다
- 우선순위: 콘텐츠(책방·토론)의 완성도가 먼저다. 연동은 **문집 주문 플로우 안쪽에만** 반영하고, 판형·분량 같은 제작 사양이 책방·토론 화면으로 새어 나오지 않게 한다
- 부수 효과: 지어낸 사양 위에 세운 주문 플로우에는 근거가 없다. 문서에 맞추자 근거 없이 정했던 규칙들(취소 마감선·배송 단계)이 실제 근거를 갖게 됐다 — [[D-034]]
- 부수 효과: **표지·제본은 고르는 축이 아니다** — 판형 하나가 표지 유형·제본·페이지 범위·가격을 함께 결정한다. 공개 페이지의 표지/제본 안내는 선택지가 아니라 사양 설명이다. 레이플랫 판형은 표준 3종에 없고 펼침면 PDF라 제외
- 연결: PLAN §5-1, [[D-034]], [[D-035]]

## D-034 주문 상태를 벤더 상태와 분리하고 배송중 단계 삭제 (2026-07-30)

- 선택지: 우리 8단계 유지 / 벤더 상태를 그대로 노출 / 우리 상태 유지 + 벤더 상태 별도 보관
- 결정: **우리 상태는 사용자 언어로 유지하고 벤더 상태를 `Order.vendorStatus`·`vendorOrderUid`·`trackingNumber`에 따로 보관**, 매핑은 `shared/bookprint/status-map.ts` 한 곳. 벤더 상태는 어드민에만 노출. **`IN_TRANSIT`(배송 중)은 삭제** — 벤더는 `SHIPPED → DELIVERED`뿐이라 대응이 없다. 8단계 → 7단계
- 이유: 최종 사용자에게 "결제완료·PDF준비완료"는 의미가 없다. 파트너사가 벤더 상태를 그대로 노출하지 않는 것도 같은 이유다. 반대로 근거 없이 만든 '배송 중'은 문서에 대응이 없어 삭제하는 쪽이 정직하다
- 파생: 취소 마감선(접수·확인까지)의 근거가 **"발주 전"** 으로 명확해졌다 — 발주하면 충전금이 차감되고 제작 큐에 들어간다. 배송 후 환불·재제작은 벤더 API 밖(관리자 승인 절차)이므로 **파트너사 CS 절차**로 정의하고, 재제작은 원 주문을 `externalRef`로 참조하는 새 벤더 주문으로 본다
- 연결: [[D-013]](전이 맵), [[D-033]]

## D-035 페이지 규칙은 주문서에서 검증한다 (2026-07-30)

- 이유: 북프린트는 페이지 규칙 위반을 **업로드에서 통과시키고 주문 생성에서 400**으로 막는다 — 사전 검증이 파트너 책임이라는 뜻이다. 주문을 다 만든 뒤 운영자가 반려하면 사용자는 왜 막혔는지 모른 채 기다린다. 원칙: 사용자가 손쓸 수 있는 실패는 사용자 화면에서 막는다

## D-036 제작처 이벤트 수신 로그를 별도로 남긴다 (2026-07-30)

- 문제: 벤더의 `PDF_READY → CONFIRMED → IN_PRODUCTION`이 우리 '문집 제작' 한 단계로 접히다 보니([[D-034]]), 제작 확정·제작 시작 이벤트를 받아도 진행 이력에는 아무 변화가 없다. 운영자 화면에서는 발주 뒤 아무 일도 일어나지 않은 것처럼 보인다
- 선택지: 우리 진행 이력에 같은 상태로 행을 더 쌓기 / 별도 수신 로그 테이블

## D-037 운영자 상세는 모달이 아니라 페이지 (2026-07-31)

- 결정: **셋 다 페이지로.** `/admin/orders/[orderId]`, `/admin/members/[memberId]`, `/admin/clubs/[clubId]`. 서로 오갈 수 있게 상세마다 상대 화면으로 가는 버튼을 두고, 되돌아가기는 브라우저 히스토리를 쓴다(직접 URL 진입이면 목록으로)

- 연결: [[D-030]], [[D-031]]

## D-038 운영자 목록 필터는 URL 쿼리에 둔다 (2026-07-31)

- 선택지: 화면 밖 스토어(Zustand)에 보관 / URL 쿼리를 단일 소스로
- 결정: **URL 쿼리가 단일 소스.** 주문 관리(상태·클럽·정렬·검색·기간·처리대기·페이지·표시건수)와 회원 관리(클럽·검색·페이지·표시건수) 모두 `?status=...&page=2` 형태로 주소에 실린다. 기본값(1페이지·20건·최신순)은 URL에 남기지 않아 링크가 지저분해지지 않게 하고, 필터 조작은 `router.replace`로 히스토리를 쌓지 않는다
- 이유: 운영자는 필터 조합을 **동료에게 링크로 보낸다** — "처리 대기만, 밑줄과 여백, 이번 주"를 말로 설명하지 않아도 되게. 브라우저 뒤로 가기로 이전 조건이 되살아나는 것도 URL을 쓰면 따라온다. 스토어에만 두면 새로고침에도 사라진다
- 유지한 것: "다른 메뉴에 갔다 돌아와도 필터가 살아 있어야 한다"는 요구는 그대로다. 스토어는 필터를 들고 있는 대신 **마지막 쿼리스트링만 기억**하고, GNB 링크가 그것을 붙인다 (URL = 단일 소스, 스토어 = 최근 위치 기억)
- 상세 상단 이동은 두 갈래다 — **뒤로**(히스토리)와 **○○ 관리**(그 목록). 하나로 합치면 라벨과 실제 이동이 어긋난다: 회원 상세에서 넘어온 클럽 상세에서 '클럽 관리'를 눌렀는데 회원 상세로 돌아가는 식
- 연결: [[D-031]](어드민 목록), [[D-037]](상세를 페이지로)

## D-039 읽을 예정인 책에도 코멘트를 막지 않는다 (2026-07-31)

- 선택지: 완독(또는 읽는 중) 책에만 코멘트 허용 / 상태와 무관하게 허용하고 문구로 안내
- 결정: **막지 않는다.** 대신 책 상태별로 입력창 문구를 달리해 기대를 맞춘다 — 읽을 예정이면 "기대되는 점이나 일정을 나눠 보세요", 읽는 중이면 "지금까지 읽은 데까지 이야기해 보세요. 뒷부분은 접어 두고요"
- 이유: 이 기획의 출발점인 오픈채팅 관찰에서, 읽기 전부터 대화가 오간다 — "이 책 왜 골랐어요?", "언제부터 시작하나요?", "저 예전에 읽었는데 좋았어요". 막으면 그 책의 스레드가 비고 사용자는 왜 안 되는지 부딪힌다. **모임 운영 대화가 책 단위로 쌓이는 것**이 채팅방과 다른 지점인데 그걸 스스로 잘라내게 된다
- 콘텐츠 품질은 이미 다른 규칙이 지킨다: 문집에는 완독 책만 실린다(`ORDER_BOOK_NOT_DONE`). 읽기 전 잡담이 문집을 어지럽힐 일은 없으므로 규칙을 하나 더 둘 이유가 없다
- 스포일러는 상태 제한으로 해결되지 않는다 — '읽는 중'에도 똑같이 생긴다. 페이지·인용 앵커로 "어디까지 읽었는지" 맥락을 주는 쪽이 실질적인 방어다
- 연결: [[D-007]](책 단위 토론), PLAN §1·§3 F2

## D-040 문집에는 그 모임의 책만 담는다 (2026-07-31)

- 선택지: 회원이 가입한 여러 클럽의 완독 책을 한 문집에 섞을 수 있게 / 주문한 클럽의 책만
- 결정: **그 클럽의 책만.** 서버가 수록 책의 `clubId`를 검증해 다른 클럽 책이 섞이면 `ORDER_BOOK_INVALID`로 거절한다. 화면에도 현재 클럽의 책만 노출하므로 사용자가 막다른 길을 만나지 않는다
- 이유:
  - 문집은 **모임의 기록물**이다(PLAN §1). 여러 클럽 책을 섞으면 개인 독서 기록물이 되고, 이 서비스가 개인 독서 노트와 구별되는 지점이 사라진다
  - 문집에는 **다른 회원의 코멘트**가 실린다. A클럽 토론을 B클럽 문집에 싣는 것은 A클럽 멤버가 동의하지 않은 사용이다 — 클럽 경계가 곧 콘텐츠 접근 경계다
  - `Order.clubId`가 단일 값이다. 섞으면 이 주문이 어느 클럽 것인지 정의되지 않고, 운영자의 클럽 필터·클럽 상세의 '이 클럽 주문'도 의미를 잃는다
  - 표지에 모임 이름·기간이 들어가는데, 여러 모임이면 무엇을 쓸지 정할 수 없다
- 로드맵: "내가 읽은 책 전부로 만드는 **개인 문집**"은 성격이 다른 별개 상품이라 PLAN §8로 미룬다
- 연결: [[D-015]](회원-모임 다대다), PLAN §1·§5

## D-041 헤더의 팝업 UI는 지연 로딩한다 (2026-07-31)

- 선택지: 전부 정적 import(단순) / 열릴 때만 받는 지연 로딩
- 결정: **로그인 모달·멤버 메뉴를 `next/dynamic`으로 분리.** 로그인 모달은 비로그인일 때만 렌더하고, 멤버 메뉴는 아바타를 처음 누를 때 마운트한 뒤 계속 유지한다
- 이유:
  - 헤더는 전 라우트에 있어, 헤더가 정적으로 import한 것은 **모든 페이지의 첫 로드 비용**이 된다. 실측 결과 로그인 모달이 끌고 오던 `Dialog`·`Tabs`·`Skeleton`과 멤버 메뉴의 `Menu`·`Popover`·`Modal`이 모달을 쓰지 않는 랜딩·운영자 목록에도 실려 있었다
  - 둘 다 **클릭해야 열리는 화면**이라 첫 페인트에 필요 없다. 랜딩 306→285KB(gzip), `/admin` 305→283KB
  - 언마운트가 아니라 **마운트 유지**로 닫는다 — 언마운트하면 닫힘 애니메이션이 잘린다
  - 첫 클릭 지연은 아바타 hover·focus 시점의 프리페치로 덮는다. 내 클럽 목록 조회는 헤더에 남겨, 메뉴가 열린 뒤 항목이 차면서 높이가 튀지 않게 했다
- 한계: 남은 공통 비용 283KB(gzip) 중 ~182KB는 React·Next 런타임이라 손댈 수 없고, 나머지는 MUI 코어다. 'MUI 우선' 컨벤션을 유지하는 한 여기가 현실적인 바닥
- 연결: [[D-024]](랜딩·로그인 모달), CLAUDE.md 컨벤션(MUI 우선)

## D-042 '경로가 없음'과 '대상이 없음'을 다르게 안내한다 (2026-07-31)

- 선택지: 조회 실패를 한 가지 화면으로 처리 / 잘못된 경로와 없는 대상을 갈라 안내
- 결정: **두 갈래.** 존재하지 않는 경로는 공통 404(`app/not-found.tsx`)가 받고, 경로는 맞지만 그 데이터가 없는 경우는 각 화면이 무엇을 못 찾았는지 밝힌다 — "책 정보를 찾을 수 없어요", "주문 정보를 찾을 수 없어요"
- 이유:
  - 사용자가 알아야 하는 게 다르다. 주소를 잘못 친 것과, 주소는 맞는데 그 책이 지워진 것은 **다음 행동이 다르다**
  - **없는 대상에 '다시 시도'를 권하면 영원히 실패하는 버튼**이 된다. 404 응답이면 재시도를 감추고 돌아갈 곳만 남긴다 (`QueryErrorView`)
  - Next 기본 404는 영문 흑백 화면에 GNB도 돌아갈 길도 없다. 루트 `not-found.tsx`는 레이아웃 안에서 그려져 헤더·푸터가 유지된다
  - 판정 기준은 HTTP 404 하나 — 백엔드가 `BOOK_NOT_FOUND`·`ORDER_NOT_FOUND` 등을 이미 404로 내려주므로 프론트에 별도 코드 목록을 두지 않는다 (D-028 연장)
- 함께: 예기치 못한 렌더 오류는 `app/error.tsx`가 레이아웃 안에서 받아 '다시 시도'를 제공한다 — 화면 하나가 무너져도 서비스 밖으로 튕기지 않게
- 연결: [[D-028]](에러 계약), QA.md §E

## D-043 폼 에러는 고치기 시작하면 거둔다 (2026-07-31)

- 결정: 인풋을 수정하는 순간 그 필드의 에러를 지운다. 여러 칸이 함께 틀린 경우(함께 읽기 시작·끝)는 두 칸을 붉게 표시하고 문구는 아래 한 줄로 모은다
- 이유: 책 추가 폼에서 참여 회원만 이 규칙을 지키고 제목·저자·코멘트는 제출 전까지 붉은 문구를 붙잡고 있었다 — 같은 폼 안에서 반응이 갈리면 무엇이 아직 문제인지 읽히지 않는다
- 기간 역전(시작 > 끝)은 서버가 이미 `BOOK_PERIOD_INVALID`로 막고 있었으나 화면이 토스트로만 받았다. 클라이언트에도 같은 규칙을 두어 해당 칸에서 바로 알린다 — 검증의 단일 소스는 서버, 화면은 그 규칙을 앞당겨 보여줄 뿐
- 연결: [[D-028]](에러 계약), QA.md §E
