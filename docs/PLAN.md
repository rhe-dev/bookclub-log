# 북클럽 로그 (BookClub Log) — 기획서

> 온라인 독서모임의 **책방(아카이브)** 서비스. 모임이 함께 읽은 책과 토론을 책 단위로 쌓고, 그 기록을 **모임 문집(실물 책)** 으로 만든다.
> 콘텐츠(모임의 책과 토론)가 본체이고, 책 제작은 그 위의 부가 기능이다.

---

## 1. 문제 정의

- 오픈채팅 독서모임은 정한 시간에 모여 실시간으로 대화하는 방식이라 대화 자체는 잘 굴러간다. 문제는 기록이다 — **여러 책의 진행 기록이 한 스크롤에 계속 쌓여** 언제 무엇을 읽었는지 다시 보기 어렵고, 여러 이야기가 동시에 오가면 **순서가 뒤섞여** 어떤 대목에 대한 말이었는지 알 수 없게 된다.
- 좋은 코멘트가 오가도 **책 단위로 모이지 않아** 모임에 남는 형태가 없다.
- 책을 좋아하는 사람들의 모임일수록 **실물로 남기고 싶은 욕구**가 크다. 흩어진 토론의 종착지로 '모임 문집'은 자연스러운 결말이다.

**기획 배경**: 과제 안내문의 예시 중 '독서 노트'에서 힌트를 얻었다. 마침 사서인 지인이 오픈채팅으로 온라인 독서모임을 운영하는 것을 지켜보던 참이었다.

**서비스가 해야 할 것 세 가지**: ① 어떤 책을 언제 읽었는지 다시 보기 편하게 ② 그 책에 달린 이야기를 이어가기 편하게 ③ 나눈 내용이 기록으로 남게. 그리고 이렇게 쌓인 토론을 문집으로 묶는다.

**서비스 성격 — 실시간성이 낮다 (의도)**: 같은 책을 읽고 소감을 나누는 데 같은 시간에 접속할 필요는 없다. 시간 맞추기가 어려운 요즘에는 **각자 자기 속도로 읽고 남긴 것이 모여 토론이 되는** 편이 현실적이다. SNS에서 보이는 **교환독서**(책을 주고받으며 서로가 남긴 밑줄·메모를 읽는)를 온라인으로 옮긴 모습에 가깝다. 그래서 **코멘트 작성 기간을 제한하지 않는다** — 읽기 전·읽는 중·완독 후 언제든 남길 수 있고(D-039), 함께 읽는 기간이 지나도 막지 않는다. 책의 기간·모임일은 "언제쯤 같이 읽었는지"를 남기는 기록이지 잠금장치가 아니다. 오프라인·화상 모임을 병행하는 모임이라면 그 자리는 그대로 두고, 이 서비스는 그 전후에 남는 것을 맡는다 (D-045).

**인쇄 API 관점**: 모임 문집은 같은 책을 **한 번에 여러 부(멤버 수만큼)** 만든다. 단체 대량 주문에 비하면 작은 구매지만 개인 1부 주문보다는 크고, 모든 주문이 기본적으로 여러 부이며 그 배수가 모임 수만큼 반복된다 — 크지 않아도 꾸준한 수요처다.

**포지셔닝**: 이 서비스는 **북프린트 API(api.sweetbook.com)를 연동하는 파트너사**다. 본체는 독서모임 기록이고, 그 기록을 북프린트로 실물 책으로 만든다. 실제 API를 호출하지는 않지만(외부 의존 배제 요건) **판형·페이지 규칙·주문 상태·에러 계약·SLA는 공개 문서 그대로 재현**한다 — §5-1.

## 2. 타겟 사용자

**A — 모임장 (30대, 사서)**

- 오픈채팅 기반 5\~6인 온라인 독서모임 운영. 월 1권.
- 책 선정·일정 등록을 챙기고, 문집 주문도 대개 이 사람이 한다.
- 주 사용 기기는 **데스크톱**.

**B — 회원 (20\~30대 직장인)**

- 출퇴근길 **모바일**로 토론 참여. 인상 깊은 문장에 짧은 코멘트를 남기고, 다른 회원의 코멘트에 답글을 단다. (한 손, 1\~2분)

**C — 운영자**

- 주문 내역 관리(단계 진행·제작처 발주), 회원·모임 조회. 주 사용 기기는 **데스크톱**.
- 어드민도 결국 이 웹의 사용자다 — 별도 화면이라고 설계 기준에서 빼지 않는다.

**설계 함의**

- 토론(코멘트·답글)은 **모바일 우선** — 빠른 작성, 큰 터치 타겟.
- 책 등록·문집 제작은 한 번에 정할 게 많아 **단계형 흐름**. 주로 데스크톱에서 쓸 것으로 본다.
- 다만 **문집 주문은 모임장 전용이 아니다.** 모임 단위가 아니라 회원 개인이 자기 몫으로 주문할 수도 있어, 주문 화면은 **모바일에서도 끝까지 진행**할 수 있어야 한다.
- 운영자 화면은 데스크톱 우선이되, 모바일에서 열어도 **카드로 접지 않고 같은 테이블을 가로 스크롤**로 본다 — 컬럼 간 비교가 운영자에게 필요한 정보다 (D-031).
- 회원 구분(누구의 코멘트인지·마이페이지)은 필수지만, 비밀번호 인증은 불필요 → **계정 선택만으로 로그인되는 목 로그인** (D-003·D-024).

## 3. 핵심 사용자 플로우

- **F0. 진입**: 서비스 소개 랜딩(`/`) → 로그인 모달에서 계정 선택(인증 없는 목 로그인) → 첫 가입 모임 책방 진입. 여러 모임 가입 회원은 GNB에서 모임 전환 (D-024)
- **F1. 책 등록 (모임장)**: 책방 → `+ 책 추가` → 서지정보(제목·저자·출판사)·표지(색+이모지)·모임 날짜/기간·참여 회원 → 저장
- **F2. 토론**: 책 상세 → 코멘트 작성(선택: 페이지·인용 문장 지정) → 다른 회원이 답글·공감(좋아요) → 스레드로 쌓임. 내 코멘트는 수정·삭제 가능(삭제는 소프트 딜리트)
- **F3. 문집 주문 (4단계)**: 책방에서 `문집 만들기` → ①수록할 책 선택 → ②수록 내용 확인(**예상 분량 N쪽** 산출) → ③**판형 + 표지**(분량으로 제작 가능한 판형만 활성, 표지 색·이모지 미리보기) → ④제목·부수 확인(**예상 제작비·예상 수령일**) → 주문(주문자 = 현재 멤버) → **마이페이지에서 단계별 날짜와 함께 상태 확인, 배송 완료 후 구매 확정**
- **F4. 주문 처리 (운영자)**: `/admin` → 주문 목록 → 주문 상세에서 **①사양 검증(판형·페이지·증분) → ②문집 PDF 생성 → ③북프린트 발주** → 이후 제작·배송 단계는 **북프린트 웹훅 수신으로 자동 전이**(데모는 이벤트 시뮬레이터) → 모든 전이가 날짜·주체와 함께 이력에 기록

```
                    createdAt, updatedAt, deletedAt?)

                    bookSpecUid, coverColor, coverEmoji,      ← 판형·표지 (§5-1)

                    trackingCarrier?, trackingNumber?)        ← 북프린트 연동 (§5-1)

OrderStatusHistory (id, orderId, fromStatus?, toStatus, changedAt, actor: USER | ADMIN | VENDOR,
                    reason?: OrderIssueReason, reasonDetail?, adminNote?)  ← 사유(D-025)·운영자 메모(D-031)

OrderStatus — 순방향 7단계:
  RECEIVED(주문 접수) → CONFIRMED(주문 확인) → IN_PRODUCTION(문집 제작)
  → PRODUCED(제작 완료) → SHIPPED(배송 시작) → DELIVERED(배송 완료)
  → PURCHASE_CONFIRMED(구매 확정)
+ 분기 4 (D-013):
  CANCELED(취소)            ← 접수·확인에서만(= 발주 전), 주문자·관리자
  REFUND_REQUESTED(환불 요청) ← 배송완료에서, 주문자 → REFUNDED(환불 완료, 관리자)
  REMAKE_REQUESTED(재제작 요청) ← 배송완료에서, 주문자 → 승인 시 IN_PRODUCTION 재진입(관리자)
  종결 상태: PURCHASE_CONFIRMED · CANCELED · REFUNDED
```

- **토론 스레드**: `parentId` 1단계(코멘트 → 답글). 페이지·인용 문장은 선택 입력 앵커. 코멘트는 작성자가 **수정(updatedAt)·삭제 가능**하며, 답글이 달린 코멘트를 지워도 스레드가 끊기지 않도록 '삭제된 코멘트'로 자리를 유지한다.
- **소프트 딜리트 원칙**: 삭제는 `deletedAt` 마킹을 기본으로 한다(Comment·Book). 토론 무결성과 문집 수록 이력을 보존하고, 하드 딜리트는 하지 않는다.
- **주문 상태**: 순방향 7단계 + **명시된 분기만** 허용(위 전이 맵), 그 외 역행·건너뛰기는 서버에서 거부. 제작·배송 단계는 운영자가 임의로 누르는 것이 아니라 **북프린트 웹훅 수신으로 전이**된다 (§5-1). 단계 진행·환불 처리·재제작 승인은 운영자(ADMIN), **취소(제작 전)·구매 확정·환불/재제작 요청은 주문자(USER)만** 가능. 모든 전이는 날짜와 함께 이력으로 남겨 마이페이지·관리자에서 단계별 날짜를 확인할 수 있다. 문집은 주문 제작(POD) 상품이므로 단순 변심 환불·교환은 없고(전자상거래법 §17 청약철회 제한), 배송 후 하자 시에만 환불 또는 재제작 — POD에는 재고 교환이 없어 구제책이 '재제작'이다 (D-013).
- **식별자 전략**: 모든 노출 모델에 publicId(cuid, unique)를 두고 **API 경로·응답에는 publicId만 사용**. 내부 PK·FK는 자동증가 int로 유지해 조인 성능·디버깅 편의를 지킨다 (D-014).
- **배송은 상태로만 표현**: 주소 입력·택배 연동 등 실제 배송 기능은 구현하지 않는다(안내문 제외 대상). 택배사·송장번호는 벤더 웹훅이 주는 값으로 표시만 한다. 실물 제작 서비스의 주문 라이프사이클을 상태 머신으로 반영하는 것이 목적.
- **회원-모임은 다대다**: Member는 전역 회원이고 소속·역할은 ClubMember(가입)로 관리한다(D-015). UI도 멀티 모임을 반영 — 세션 = 멤버 + 현재 모임, GNB에서 모임 전환, 역할(모임장/멤버)은 모임별 (D-024). 시드에 두 모임·멀티 모임 회원 포함.

## 5-1. 북프린트 API 정합 (파트너사 관점)

> 출처: `https://api.sweetbook.com/docs/llms-full.txt` + 공개 제품 안내 페이지 (2026-07-30 확인).
> 실제 호출은 하지 않는다(외부 의존 배제 요건). 계약만 재현하고, 벤더 호출부는 `backend/src/shared/bookprint/`의 목 클라이언트가 대신한다.

### (1) 제작 방식 — `PDF_UPLOAD` 하나로 고정

북프린트는 3가지 창작 방식(`PDF_UPLOAD` · `TEMPLATE` · `MIX_COVER_TEMPLATE`)을 제공하지만, 파트너는 보통 하나를 정해 쓴다. 우리는 **`PDF_UPLOAD`** (문서상 기본 권장):

- 문집 내지는 **코멘트 텍스트 조판**이다. 표지도 서비스 안에서 색·이모지를 조합해 고르는 흐름이라, 우리가 PDF를 만들어 올리는 방식이 이 서비스에 맞다고 봤다.
- 서비스의 책 표지 컨벤션(색 + 이모지)을 문집 표지에 그대로 이어 쓸 수 있다.
- `pageCount` 사전 고지가 필수인데, 이게 오히려 이득이다. **주문 전에 분량이 확정**되므로 페이지 규칙을 주문서에서 검증할 수 있다 — (3).
- 주문 즉시 `PDF_READY`로 승격돼 렌더링 대기 상태가 없다 → 사용자에게 설명 못 할 중간 상태가 생기지 않는다.
- 트레이드오프: 사진 사전 업로드 API(`/photos`)가 차단되고(`ERR_CREATION_TYPE_UNSUPPORTED`) 표지 템플릿 카탈로그를 쓸 수 없다. 우리는 둘 다 필요 없다.

### (2) 판형 — 표지·제본은 고르는 축이 아니다

**판형(BookSpec) 하나를 고르면 표지 유형·제본 방식·페이지 규칙·가격이 함께 결정된다.** 공개 페이지의 표지·제본 안내는 선택지가 아니라 *"이 사양이 무엇인지"* 설명이다 ("사양에 따라 둘 중 하나가 표준 적용됩니다").

즉시 주문 가능한 표준 판형 3종만 카탈로그로 노출한다.

| bookSpecUid | 이름 | 크기 | 표지/제본 | 페이지 | 문집에서의 성격 |
| --- | --- | --- | --- | --- | --- |
| `PHOTOBOOK_A5_SC` | A5 소프트커버 | 148×210 | 소프트 / PUR | **50\~200** | 단행본 느낌. 가장 '책' 같지만 50쪽 문턱 |
| `PHOTOBOOK_A4_SC` | A4 소프트커버 | 210×297 | 소프트 / PUR | 24\~130 | 넉넉한 판면. 인용·긴 글이 많은 모임 |
| `SQUAREBOOK_HC` | 스퀘어북 하드커버 | 243×248 | 하드 / PUR | 24\~130 | 소장·선물용. 1주년 기념 문집 |

`SQUAREBOOK_LAYFLAT_HC`(레이플랫, 16\~46쪽)는 **제외**한다 — 공개 페이지의 표준 3종에 없고, 사진 중심 제본이라 텍스트 문집에 맞지 않으며, 내지 PDF가 펼침면(`pageCount / 2`)이라 조판을 따로 만들어야 한다.

페이지 규칙은 공통이다: `pageMin ≤ pageCount ≤ pageMax`, `pageIncrement`(2) 배수. **위반해도 PDF 업로드는 통과하고 주문 생성에서 400으로 막힌다** → 사전 검증은 파트너 책임.

### (3) 분량 산출과 검증 시점 — 어드민이 아니라 주문서에서

우리가 내지를 조판하므로 수록 대상이 정해지는 순간 쪽수를 계산할 수 있다.

```
pageCount = 속표지 1 + 모임 소개 1 + Σ(책마다: 표제지 1 + 코멘트 수) + 맺음말 1
            → 홀수면 +1 (여백면). pageIncrement=2 충족
```

- 주문서 ②단계에 **"예상 분량 32쪽"** 을 표시한다.
- ③단계 판형 카드는 이 쪽수로 **제작 가능한 것만 활성화**하고, 불가한 판형은 이유를 함께 보여준다 — *"A5는 50쪽부터 만들 수 있어요. 책을 더 담으면 선택할 수 있어요"*.
- 최소 쪽수를 어떤 판형으로도 못 채우면 주문 진입 자체를 막고 무엇을 하면 되는지 안내한다.
- 운영자는 **발주 직전 재확인만** 한다 (어드민 상세의 사양 검증 블록).

> 원칙: **사용자가 손쓸 수 있는 실패는 사용자 화면에서 미리 막고, 운영자는 승인 전 재확인만 한다.**

### (4) 주문 상태 매핑 — 우리 말로 보여주고 벤더 상태는 따로 보관

사용자에게 "결제완료 / PDF준비완료"는 의미가 없다. 우리 상태는 사용자 언어로 두고, 벤더 상태는 `Order.vendorStatus`에 보관해 **어드민에서만** 노출한다. 매핑은 `shared/bookprint/status-map.ts` 한 곳에서 관리한다.

| 우리 상태 | 북프린트 `orderStatus` | 전이 주체 |
| --- | --- | --- |
| 주문 접수 `RECEIVED` | (벤더 주문 없음) | 주문자 |
| 주문 확인 `CONFIRMED` | (벤더 주문 없음) | 운영자 — 사양 검증 통과 |
| 문집 제작 `IN_PRODUCTION` | `PAID` → `PDF_READY` → `CONFIRMED` → `IN_PRODUCTION` | 운영자 발주 → 이후 웹훅 |
| 제작 완료 `PRODUCED` | `PRODUCTION_COMPLETE` | 웹훅 `production.completed` |
| 배송 시작 `SHIPPED` | `SHIPPED` | 웹훅 `shipping.departed` (+송장번호) |
| 배송 완료 `DELIVERED` | `DELIVERED` | 웹훅 `shipping.delivered` |
| 구매 확정 `PURCHASE_CONFIRMED` | (벤더에 없음) | 주문자 |

- **`IN_TRANSIT`(배송 중) 삭제**: 벤더는 `SHIPPED → DELIVERED`뿐이라 대응이 없다. 근거 없는 단계였다.
- **취소 마감선의 근거**: 우리가 취소를 접수·확인까지만 허용하는 것은 **그 지점이 발주 전이기 때문**이다. 발주하면 충전금이 차감되고 제작 큐에 들어간다. (벤더도 `PAID`·`PDF_READY`까지만 파트너 취소를 허용하므로, 발주 직후라면 운영자가 벤더 취소를 호출할 여지는 남는다 — 어드민 예외 액션으로 TODO)
- **환불·재제작은 벤더 API 밖**이다. 문서상 배송 후 취소·환불은 "관리자 승인 절차"로만 가능하다. 따라서 우리의 환불/재제작 요청은 **파트너사가 접수해 스위트북 고객지원과 협의하는 CS 절차**이고, 재제작은 **원 주문을 `externalRef`로 참조하는 새 벤더 주문**이 된다.

### (5) 에러 계약 — 2계층

| 계층 | 계약 |
| --- | --- |
| 벤더 ↔ 우리 백엔드 | 북프린트 그대로: 6필드 고정(`success`·`errorCode`·`message`·`data`·`errors`·`fieldErrors`), `ERR_*` 코드, `fieldErrors[].constraint` enum 6종 |
| 우리 백엔드 ↔ 프론트 | 기존 계약 유지(D-028) + `fieldErrors` 채택. 벤더 코드는 도메인 코드로 **번역**한다 |

파트너사가 실제로 하는 일이 이 번역이다. 벤더 에러를 사용자에게 그대로 던지지 않고, **재시도 가능 여부**(문서의 재시도 컬럼)에 따라 운영자에게 다른 안내를 준다 — 예: `ERR_TOO_MANY_REQUESTS`는 `Retry-After` 후 재시도, `ERR_INSUFFICIENT_CREDIT`는 충전 필요, `ERR_PAGECOUNT_INVALID`는 재시도 불가(문집 재구성).

### (6) 견적과 일정 안내

- **가격**: `priceBase + ((pageCount - pageMin) / pageIncrement) × pricePerIncrement`, × 부수, + 배송비 3,000원/주문. 주문서 ④단계와 주문 상세에 **예상 제작비**로 표시한다. 결제 수단·정산은 만들지 않는다(안내문 제외 대상).
- **SLA**: 제작 3\~4 영업일(공휴일 제외) + 배송 1\~2일(한진택배). 주문서·주문 완료·마이페이지에 **예상 수령일**로 환산해 보여주고, 단계가 진행되면 갱신한다.

## 8. 로드맵 (과제 이후 디벨롭 — README "더 시간이 있었다면")

- **커뮤니티**: 모임 밖 회원들이 소통하는 공간 — 다른 모임의 책 후기, 모임 진행 노하우 공유, 원하는 모임 찾기
- 모임 만들기·초대·가입 정식 플로우 + **모임 정원**. 정원은 초대와 한 몸이라 함께 도입한다 — 상한 근거는 부수 상한(100부)과 판형 페이지 상한(130\~200쪽)에서 나온다 (D-044)
- **기간이 시작됐는데 아직 '읽을 예정'인 책 알려주기** — 자동 전환이 아니라 힌트. 바꾸는 판단은 모임장이 한다 (D-046)
- 표지 이미지 업로드, 문집 구성 미리보기 고도화
- **토론 알림**: 답글·공감·새 코멘트를 알려 재방문 계기를 만든다 — 실시간 연결 없이 기록이 쌓이는 구조라 알림이 그 역할을 맡는다 (D-045)
- **개인 기록과 개인 문집**: 모임 밖 개인 독서도 기록하고, 여러 모임의 책과 함께 내 독서 전체를 한 권으로 — 모임 문집과 성격이 다른 별개 상품 (D-040)
- **운영자 계정 구분과 CS 기능**: 루트·직원 권한 분리 + 문의 접수·답변·처리 이력. 운영자 메모가 그 첫 조각
- **운영측의 이달의 추천책**: 매달 한 권을 모임들에 제안 — 모임장의 선정 부담을 덜고, 여러 모임이 같은 책을 읽으면 커뮤니티로 이어질 소재가 된다

## 9. 기술 스택과 선택 이유

- **Frontend**: Next.js (App Router), TypeScript, TanStack Query, Zustand, Axios, MUI
- **Backend**: NestJS, Prisma, PostgreSQL
- **실행**: Docker Compose (db + backend + frontend), 포트는 환경변수로 변경 가능

**이유**: TypeScript 단일 언어로 프론트–백–DB를 잇는, 현재 실무에서 매일 사용 중인 조합. 제한된 기간에 학습 비용 없이 구현 완성도에 시간을 쓰기 위한 선택이다. 스키마→API→화면의 타입을 일관되게 유지할 수 있고, 서버 상태(TanStack Query)와 클라이언트 상태(Zustand)를 분리해 관리한다. UI는 검증된 컴포넌트(MUI)를 사용해 화면 판단(흐름·문구·상태 표시)에 집중한다.
