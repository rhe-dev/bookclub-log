# 북클럽 로그 (BookClub Log)

**온라인 독서모임이 함께 읽은 책과 토론을 책 단위로 쌓고, 그 기록을 실물 문집으로 만드는 서비스입니다.**

---

## 1. 서비스 소개

온라인 독서모임이 **어떤 책을 언제 함께 읽었는지, 그 책에서 어떤 이야기가 오갔는지**를 책 단위로 쌓아 두는 서비스입니다. 모임이 끝나도 기록이 흩어지지 않고, 충분히 쌓이면 그대로 **실물 문집**으로 묶을 수 있습니다.

세 가지를 할 수 있게 만드는 것이 목표였습니다.

- 어떤 책을 언제 읽었는지 다시 보기 편하게.
- 그 책에 달린 이야기를 이어가기 편하게.
- 나눈 내용이 기록으로 남게.

> 이 주제를 고른 배경과 이유는 [§7 설계 의도](#7-설계-의도)에 적었습니다.

### 타겟 사용자

|     | 사용자                     | 하는 일                                                   | 주 사용 기기 |
| --- | -------------------------- | --------------------------------------------------------- | ------------ |
| A   | **모임장** (30대, 사서)    | 5\~6인 온라인 독서모임 운영. 책 선정·일정 등록, 문집 주문 | 데스크톱     |
| B   | **회원** (20\~30대 직장인) | 토론 참여 — 인상 깊은 문장에 코멘트, 답글, 공감           | 모바일       |
| C   | **운영자**                 | 주문 내역 관리(단계 진행·제작처 발주), 회원·모임 조회     | 데스크톱     |

이 세 사람이 화면 설계의 기준입니다. 각자를 위해 어떤 판단을 내렸는지는 [§4 사용자 경험 설계](#4-사용자-경험uiux-설계)에 정리했습니다.

### 주요 기능

- **모임 책방** — 지금 읽는 책 + 지난 책 아카이브. 상태(읽을 예정·읽는 중·완독) 필터, 함께 읽는 기간·모임일·참여 멤버, 색·이모지 표지.
- **책 단위 토론** — 페이지·인용 앵커가 달린 코멘트, 답글 1단계, 공감. 채팅과 달리 이야기가 책에 묶여 남습니다.
- **문집 만들기** — 4단계 주문서(책 선택 → 수록 확인 → 판형·표지 → 부수·견적). 코멘트 수로 예상 분량을 계산해 만들 수 있는 판형만 활성화합니다.
- **주문 추적** — 사용자 말로 된 상태와 4그룹 진행 스텝, 예상 수령일·다음 행동 안내, 취소·구매 확정·환불·재제작 요청.
- **운영자 화면** — 주문 관리(필터·일괄 처리·CSV), 제작처 발주·이벤트 수신, 회원·모임 조회와 운영자 메모.

## 2. 실행 방법 (Docker)

### 필요한 것

Docker Desktop만 있으면 됩니다. `.env` 파일을 만들 필요도 없습니다 — compose에 기본값이 들어 있습니다.

```bash
git clone https://github.com/rhe-dev/bookclub-log.git
cd bookclub-log
docker compose up --build
```

접속:

|                    | 주소                           |
| ------------------ | ------------------------------ |
| 서비스             | http://localhost:3000          |
| API 문서 (Swagger) | http://localhost:4000/api/docs |

첫 실행 시 DB 마이그레이션과 시드가 자동으로 돌아갑니다 (모임 2개 · 회원 8명 · 책 18권 · 코멘트 77개 · 주문 17건). **비밀번호 없이 계정만 고르면 바로 둘러볼 수 있습니다.**

- **회원으로 보기**: `로그인` → 계정 선택 (모임장을 보려면 `서지원`).
- **운영자로 보기**: `로그인` → `관리자` 탭 → `운영자로 들어가기`.

### 포트 변경

포트가 이미 사용 중이면 `.env.example`을 복사해 값만 바꾸면 됩니다.

```bash
cp .env.example .env
# .env 에서 FRONTEND_PORT / BACKEND_PORT / DB_PORT 수정
docker compose up --build
```

> ⚠️ **`BACKEND_PORT`를 바꿀 때는 반드시 `--build`가 필요합니다.**
> 프론트엔드가 호출할 API 주소(`NEXT_PUBLIC_API_URL`)는 Next.js 빌드 시점에 번들에 박힙니다.
> `--build` 없이 포트만 바꾸면 화면은 뜨지만 이전 포트를 호출해 데이터가 전부 실패합니다.
> `FRONTEND_PORT`·`DB_PORT`만 바꾼다면 재기동으로 충분합니다.

### 종료·초기화

```bash
docker compose down      # 종료 (데이터 유지)
docker compose down -v   # 종료 + DB 초기화 (다음 기동에 시드 재생성)
```

시드는 멱등합니다 — 데이터가 이미 있으면 건너뛰므로 재시작해도 중복되지 않습니다.

## 3. 완성한 레벨

**Lv1 · Lv2 · Lv3 모두 구현했습니다.**

### Lv1 — 서비스 플로우

랜딩 → 계정 선택 입장 → 책방 → 책 상세(토론)까지 이어집니다.

#### ① 모임 책방의 책 등록·수정·삭제

모임이 **함께 읽는 책**을 등록합니다. 개인 서재가 아니라 모임의 커리큘럼에 가까워서, 등록·수정·삭제 권한은 **모임장에게만** 있습니다. UI에서 버튼을 감추는 것으로 끝내지 않고 서버에서 검증합니다 — 다른 모임의 모임장이 남의 모임 책을 건드리는 것도 거부합니다.

한 권에 담기는 값입니다.

| 값                   | 설명                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------ |
| 제목 · 저자 · 출판사 | 서지정보. 제목·저자는 필수                                                                 |
| 표지                 | 색 8종 + 이모지 16종 조합. 외부 도서 API를 쓰지 않는 대신 모임이 직접 고릅니다             |
| 상태                 | 읽을 예정 · 읽는 중 · 완독. 책방 필터와 문집 수록 자격(완독만 문집 제작 가능)의 기준입니다 |
| 함께 읽는 기간       | 시작일 \~ 종료일. 시작이 종료보다 뒤면 에러 표시                                           |
| 모임일               | 이 책으로 이야기하는 날                                                                    |
| 참여 회원            | 모임 멤버 중 이 책을 함께 읽는 사람. 최소 1명                                              |

삭제는 소프트 딜리트입니다. 이미 문집에 실린 책이 사라지면 주문 이력이 깨지기 때문입니다.

상태는 기간이 지나도 자동으로 바뀌지 않고 **모임장이 직접** 바꿉니다 — 이유는 §4 '만들지 않기로 판단한 것'에 적었습니다.

#### ② 책 단위 토론

책 상세 페이지가 곧 그 책의 토론방입니다.

- **코멘트**(페이지·인용 앵커는 선택 입력) / **답글 1단계** / **공감**(멤버당 1회 토글).
- 수정·삭제는 작성자만 — 수정하면 '수정됨' 표기, 답글 달린 코멘트는 지워도 **'삭제된 코멘트'로 자리가 남아** 답글이 고아가 되지 않습니다.
- 내 코멘트는 마이페이지에 모이고, 클릭하면 그 토론으로 이동합니다.

#### ③ 회원과 모임의 관계

**개인이 먼저 있고, 그 개인이 여러 모임에 참여하는 구조**입니다. 모임마다 다른 사람들과 다른 책을 읽으므로, 역할도 모임마다 다릅니다 — A모임에서는 모임장이면서 B모임에서는 회원일 수 있습니다.

그래서 화면의 거의 모든 것이 "**지금 어느 모임에 있는가**"에 따라 달라집니다. 책방에 보이는 책, 문집에 담을 수 있는 책, 모임장 권한이 전부 현재 모임 기준입니다. 모임 전환은 자주 일어날 동작이라 **GNB 멤버 메뉴와 마이페이지 두 곳**에 접근점을 뒀습니다.

**이 서비스는 회원제입니다.** 개인이 가입해 여러 모임에 참여하는 것이 제품의 모습이지만, 회원 인증은 과제의 구현 대상이 아니어서(안내문: "결제·배송·회원 인증은 구현 대상이 아닙니다") 가입·로그인 대신 **계정을 고르면 즉시 로그인되는 데모**를 뒀습니다. 빠진 것은 비밀번호·세션 관리뿐이고, "누가 쓴 코멘트인지" 같은 **회원 관점은 그대로 유지**됩니다. 모임·회원 탈퇴는 디벨롭 사항으로 남겼습니다(§7).

### Lv2 — 주문과 상태 관리

**상태 전이는 전부 서버에서 검증합니다.** 순방향 7단계 + 허용된 분기만 통과합니다.

```
접수 → 확인 → 제작 → 제작완료 → 배송시작 → 배송완료 → 구매확정
  └ 취소(접수·확인에서)   └ 환불요청 → 환불완료
                          └ 재제작요청 → 제작 재진입
```

역행·건너뛰기·종결 후 전이·권한 없는 전이를 서버가 거부합니다. — 구매 확정·취소·환불/재제작 요청은 주문자만, 단계 진행·환불 처리·재제작 승인은 운영자만 할 수 있습니다.

검증 근거: **유닛 테스트 24개**(전이 맵) + **API 시나리오 44항목** — 역행·건너뛰기·권한 위반·중복 발주가 실제로 거부되는지 도커 기동 상태에서 확인합니다 (`scripts/regression-api.sh`).

#### ① 주문자 화면 (마이페이지)

- 내가 주문한 문집을 **모임과 무관하게 한곳에서** 봅니다 — 주문번호·판형·분량·금액·수록 책, 배송 시작 후엔 송장번호까지.
- 상태·스텝·다음 행동 안내는 §4 '주문한 뒤'에 정리했습니다. **진행 이력**은 단계별 날짜와 함께 펼쳐 볼 수 있습니다.
- 상태에 따라 가능한 액션만 노출합니다 — 접수·확인=취소 / 배송 완료=구매 확정·환불 요청·재제작 요청 / 종결=없음.
- 환불·재제작은 **사유 필수** — 정형 4종 + 기타(직접 입력 5\~500자). 접수된 사유는 이력에 남아 운영자가 봅니다.

#### ② 운영자 화면 (`/admin`)

- **목록** — 주문일시·최근 변경·상태·모임·주문자·판형·금액을 테이블 한눈에. 필터(기간·상태·통합 검색·정렬)와 '처리 대기만' 토글, GNB 대기 건수 배지. 필터 조합은 **URL 쿼리**에 실려 공유·복원됩니다.
- **일괄 처리** — 선택한 주문들의 공통 다음 단계만 제안, 실패 건은 건너뛰고 결과 보고.
- **CSV 3종** — 선택 항목 / 현재 페이지 / 필터 전체. 파일명에 범위·필터가 드러나고(`orders_RECEIVED_pending`), 엑셀 한글 호환(BOM) + 사유·운영자 메모 포함.
- **상세** — 전이 맵상 **지금 가능한 다음 단계만** 버튼으로 노출, 단계마다 운영자 메모, 제작처 연동 패널(사양 검증 → 발주 → 이벤트 수신).

모든 전이는 **행위자(주문자·운영자·제작처)와 시각**이 함께 기록되고, 운영자가 진행한 결과는 주문자 마이페이지에 즉시 반영됩니다.

### Lv3 — 사용자 경험 설계

"누가 쓰는 서비스인가"를 먼저 정하고(§1 타겟 사용자), 그 사람 기준으로 화면과 흐름을 설계했습니다. 크게 여섯 갈래로 잡았고, **판단 근거와 구체적인 내용은 [§4](#4-사용자-경험uiux-설계)에 적었습니다.**

| 갈래        | 요지                                                                                    |
| ----------- | --------------------------------------------------------------------------------------- |
| 첫 진입     | 랜딩 → 계정 선택 → 책방.                                                                |
| 상태 표기   | "문집을 만들고 있어요" 식 라벨 + 4그룹 스텝 + 다음 행동 안내                            |
| 흐름 유지   | 스크롤 복원, 주문 후 진입 탭, 상세 화면을 모달이 아닌 페이지로, 로그아웃 시 세션 초기화 |
| 비정상 경로 | 스켈레톤·빈 상태·조회 실패·입력 검증·404 갈래 안내                                      |
| 반응형 구현 | 전 화면 반응형. 운영자 테이블은 좁은 화면에서도 테이블 유지                             |
| 요청·로딩   | 중복 견적 호출 제거, 첫 로드에 필요 없는 코드 지연, 캐싱                                |

### 추가로 한 것 — 북프린트 API 파트너사 정합

이 서비스는 **북프린트 API(api.sweetbook.com)를 연동하는 파트너사**라는 전제로 만들었습니다. 외부 의존 배제 요건에 따라 실제 호출은 하지 않지만, **공개 문서의 계약을 그대로 재현**했습니다 — 실제 연동 시 목 클라이언트만 교체하면 되는 구조입니다.

- **제작 방식** `PDF_UPLOAD` 하나로 고정 — 문집 내지는 코멘트 텍스트 조판이고, 표지도 서비스 안에서 색·이모지를 조합해 고르는 흐름이라 이 방식이 맞다고 봤습니다.
- **표준 판형 3종** — 판형을 고르면 표지 유형·제본·페이지 규칙·가격이 함께 결정되는 구조를 그대로 따랐습니다.
- **페이지 규칙 사전 검증** — `pageMin/pageMax/pageIncrement` 위반은 벤더가 주문 생성에서 400으로 막으므로 사전 검증은 파트너 책임입니다. 주문서에서 분량을 계산해 **가능한 판형만 활성화**합니다.
- **상태 분리** — 벤더 상태(`PDF_READY` 등)는 `Order.vendorStatus`에 따로 보관하고 운영자에게만 보입니다. 사용자에게 "PDF준비완료"는 의미가 없습니다.
- **웹훅 수신** — `production.completed`·`shipping.departed` 등 이벤트로 상태가 전이되고, 이력의 행위자가 `VENDOR`로 구분됩니다.
- **에러 번역** — 벤더 에러 코드를 도메인 에러 코드로 옮기고 재시도 가능 여부를 함께 판정합니다.

구현: `backend/src/shared/bookprint/` (판형 카탈로그·분량 산출·사양 검증·견적·수령일·목 클라이언트·상태 맵·에러 번역).

## 4. 사용자 경험(UI/UX) 설계

세 사람을 기준으로 설계했습니다 — **모임장**(30대, 5\~6인 모임 운영, 데스크톱), **회원**(20\~30대 직장인, 출퇴근길 모바일), **운영자**(주문 처리, 데스크톱). 상황과 기기는 §1에 적었고, 여기서는 **그 사람을 위해 어떤 화면·흐름 판단을 내렸는지**를 씁니다.

### 처음 온 사람 — 무엇을 하는 곳인지 알 수 있게

- 루트(`/`)에 **서비스 소개 랜딩**을 두어 주요 기능 3종을 간단히 소개하고, `모임 시작하기` 버튼으로 로그인한 뒤 기능을 쓰도록 했습니다.
- **비밀번호 없는 계정 선택 로그인** — 회원 관점(누구의 코멘트인지·마이페이지)은 살리면서 인증 구현 비용만 덜어내는 선택입니다. 심사자가 계정을 만들거나 자격증명을 찾을 필요가 없어 첫 진입이 막히지 않습니다. 모달에 "데모 서비스라 비밀번호 없이 계정 선택만으로 로그인돼요"라고 밝혔습니다.
- **빈 책방은 역할에 따라 다른 말을 합니다** — 모임장에게는 "첫 책을 등록해 보세요", 회원에게는 "모임장이 책을 등록하면 여기에 쌓여요". 같은 빈 화면이라도 할 수 있는 일이 다릅니다.

### 모임장 기능 — 책 등록

- 필수는 **제목·저자·참여 회원** 셋이고, 비운 채로 저장하면 해당 칸에 에러를 띄웁니다. 나머지(출판사·기간·모임일)는 나중에 채울 수 있습니다.
- **참여 회원은 모임 전원이 기본으로 선택**되어 있습니다. 대개 다 같이 읽고 빠지는 사람만 빼는 순서라, 반대로 두면 매번 전원을 다시 고르게 됩니다.
- 표지는 **색·이모지 조합**입니다. 외부 도서 검색 API를 쓰지 않고 이미지 업로드도 없이 표지를 만들기 위한 방식입니다. 실제 서비스라면 도서 검색으로 표지를 가져오는 편이 자연스러울 텐데, **외부 의존 없이 동작해야 하는 과제 조건에 맞춘 임시 결정**입니다.
- **책 상태는 직접 바꿉니다.** 기간이 시작됐다고 자동으로 넘기지 않습니다 — 독서모임은 일정이 자주 밀리는데 시스템이 날짜만 보고 바꾸면 매번 되돌려야 합니다.

### 책방과 토론 — 모임장·회원 공통

- 코멘트 입력은 **본문 하나만 필수**입니다. 페이지·인용 앵커는 접혀 있다가 필요할 때 펼치는 선택 입력이라, 그냥 감상만 남겨도 됩니다.
- **코멘트 인풋 플레이스홀더를 책 상태별로 다르게** 뒀습니다. 같은 입력창이라도 기대하는 이야기가 다릅니다.

  | 책 상태   | 플레이스홀더                                               |
  | --------- | ---------------------------------------------------------- |
  | 읽을 예정 | 아직 읽기 전이에요. 기대되는 점이나 일정을 나눠 보세요     |
  | 읽는 중   | 지금까지 읽은 데까지 이야기해 보세요. 뒷부분은 접어 두고요 |
  | 완독      | 이 책에 대한 생각을 남겨보세요                             |

- **답글은 1단계까지만** — 트리가 깊어지면 어느 말에 대한 답인지 따라가기 어렵습니다.
- **공감**은 답글을 달 만큼은 아니지만 반응하고 싶을 때의 자리입니다. 멤버당 1회 토글이라 고민할 것이 없습니다.
- 내 코멘트는 마이페이지에 모이고, 누르면 **그 토론으로 돌아갑니다.** 수정·삭제는 토론방 내에서만 가능.

### 문집 주문 — 모임장·회원 공통

**1단계 — 책 선택**

- 책방의 **모든 책을 보여주되** 완독이 아닌 책은 비활성 + 투명도로 처리했습니다. 아예 감추면 "내 책이 왜 없지?"가 되고, 보여주면 왜 못 고르는지가 드러납니다.
- **전체 선택·전체 해제** 버튼을 뒀습니다. 지난 책이 쌓인 모임일수록 하나씩 누르는 것이 일입니다.
- 선택 책 목록 패널 : 여러 권을 고르면 목록 스크롤이 길어져 **위에서 뭘 골랐는지 다시 못 봅니다.** 버튼에는 권수만 나오고요. 그래서 **선택한 책 제목을 보여주는 패널**을 붙였습니다 — 데스크톱은 옆에 플로팅으로 고정, 모바일은 하단 버튼 바로 위에 붙여 접었다 펼 수 있게 했습니다.
- **분량 부족 안내를 1단계로 옮겼습니다.** 처음에는 2단계에서 알렸는데, 그러면 무조건 이전으로 돌아가야 합니다. 지금은 `다음`을 누른 시점에 1단계에서 막습니다. 스크롤을 위아래로 오가는 화면이라, 부족 안내 배너 위치도 **하단에 고정된 다음 버튼 바로 위**에 뒀고, 책을 다시 고르거나 빼면 배너는 사라집니다.

**2단계 — 수록 확인**

- 고른 **책 권수·코멘트 수·예상 분량**을 보여줍니다.
- **코멘트가 없는 책이 섞여 있으면 배너로 알리고, 한 번에 빼는 버튼**을 함께 뒀습니다. 표제지만 들어가는 책을 빼고 싶을 수 있습니다.

**3단계 — 판형·표지**

- 판형 3종을 **모두 노출하되**, 지금 분량으로 만들 수 없는 판형은 비활성 + 이유를 함께 보여줍니다 (예: A5는 50쪽부터).
- 표지는 책 등록과 같은 **색·이모지 조합**입니다. 제작처 API가 요구하는 표지 데이터를 이미지 업로드 없이 만들기 위한 같은 방식입니다.

**4단계 — 부수·확인**

- 인쇄 부수는 **1\~100부**로 뒀습니다. 범위를 벗어난 값이 들어와도 계산이 깨지지 않게 클램프합니다.
- 부수를 바꾸면 **예상 제작비**가 바로 갱신되고, **예상 수령일**을 함께 안내합니다.

**단계 이동과 완료**

- 4단계라 화면이 바뀌는데, 특성상 **이전 단계로 돌아가 선택을 고치는 일이 자주 생깁니다.** 그래서 **다음으로 갈 때는 맨 위로**(그 단계에서 먼저 볼 것을 보여주고), **이전으로 돌아갈 때는 보던 위치로** 스크롤을 되돌립니다. 책 목록에서 중간쯤 고르다 돌아왔는데 맨 위로 튀면 다시 찾아 내려가야 합니다.
- 주문을 마치면 **주문 내용 요약**과 함께 `책방으로` · `마이페이지에서 확인` 버튼을 둡니다. 마이페이지로 갈 때는 **주문 내역 탭이 열린 채로** 들어갑니다 — 기본 탭은 내 코멘트지만, 방금 주문한 사람이 보려는 건 코멘트가 아닙니다.

### 마이페이지 주문 목록

- 상태 라벨을 **사용자 말**로 뒀습니다: `IN_PRODUCTION` → **"문집을 만들고 있어요"**, `DELIVERED` → **"배송이 완료됐어요".**
- 내부 7단계를 **4그룹(접수·제작·배송·완료) 스텝**으로 접어 보여줍니다. 사용자가 알아야 할 해상도는 그 정도입니다.
- 진행 이력은 같은 상태라도 **명사형**("제작 시작")으로 씁니다 — 타임라인은 훑는 것이라 서술형이 방해가 됩니다.
- **단계마다 다음에 무엇을 기다리거나 해야 하는지** 한 줄을 붙입니다.
  - 진행 중: "8월 5일\~8월 7일쯤 받아보실 수 있어요" (상태가 진행될수록 기준 시점이 옮겨가 안내가 좁혀집니다).
  - 배송 완료: "받으신 문집을 확인하고 구매를 확정해 주세요. 하자가 있다면 환불·재제작을 요청할 수 있어요".
  - 배송 완료는 주문자가 **판단해야 하는 유일한 분기점**이라 상태 칩 색도 진행 중과 다르게 뒀습니다.
- **환불·재제작은 제작처의 실제 정책을 따랐습니다.** 문집은 주문 제작이라 재고가 없어 교환할 물건이 없고, 단순 변심 환불도 대상이 아닙니다. 그래서 **하자가 있을 때만** 환불 또는 재제작을 접수하고, 그 사실을 확인 모달 문구에 그대로 씁니다 — "문집은 주문 제작 상품이라 하자가 있을 때만 환불을 접수할 수 있어요".

### 운영자 — 주문을 실제로 굴리는 사람

지금 다니는 회사에서 어드민을 만들며 **운영팀에서 실제로 올라오던 피드백**을 참고했습니다. 조회 조건은 최대한 열어 두고, 자주 하는 동작은 짧게 만드는 방향입니다.

**목록에서**

- 테이블은 **좁은 화면에서도 카드로 바꾸지 않았습니다.** 주문일시·상태·최근 변경을 나란히 놓고 보는 것 자체가 정보라, 테이블을 유지하고 자기 영역 안에서만 가로 스크롤하게 했습니다.
- 필터는 **주문일 기간·상태·통합 검색·정렬·표시 건수**입니다. 운영에서 "이 조건으로 뽑아 달라"는 요청이 다양하게 들어오기 때문에, 화면에서 바꿀 수 있는 축을 최대한 뒀습니다.
- 주문 상태를 직접 처리해주는 구조이므로, **`처리 대기만` 토글**로 신규 접수와 환불·재제작 요청만 걸러 봅니다. GNB에도 대기 건수를 배지로 답니다.
- **일괄 처리** — 여러 건을 골라 한 번에 넘깁니다. 선택한 주문들의 **공통 다음 단계만** 제안하므로, 접수 상태 건들을 고르면 `주문 확인`·`주문 취소`가 뜹니다. 상태가 섞여 교집합이 없으면 일괄 버튼은 사라지고 **CSV 내려받기만** 남습니다.
- 필터 조합은 **URL 쿼리**에 실려 링크로 공유되고, 다른 메뉴에 갔다 돌아와도 보던 조건이 살아납니다.

**상세에서**

- **지금 가능한 다음 단계만** 버튼으로 나옵니다. 상태별로 이렇습니다.

  | 주문 상태                    | 운영자에게 보이는 버튼                       |
  | ---------------------------- | -------------------------------------------- |
  | 주문 접수                    | 주문 확인 · 주문 취소                        |
  | 주문 확인                    | 제작 시작(발주) · 주문 취소                  |
  | 문집 제작 → 배송 완료        | 다음 단계 (보통 제작처 웹훅이 대신 넘깁니다) |
  | 배송 완료                    | 없음 — 구매 확정·환불·재제작 요청은 주문자만 |
  | 환불 요청                    | 환불 완료                                    |
  | 재제작 요청                  | 제작 재진입                                  |
  | 구매 확정 · 취소 · 환불 완료 | 없음 (종결)                                  |

- **주문자·모임 상세 화면으로 바로 가는 버튼**을 뒀습니다. CS를 처리할 때 회원 정보를 함께 보는 일이 잦은데, 매번 회원 관리로 들어가 이름이나 ID를 검색하는 것이 번거롭습니다.
- 진행 이력은 **주문자 화면과 같은 컴포넌트를 재사용**하되, 운영자에게는 **행위자와 운영자 메모**를 더 보여줍니다. 특히 제작처 웹훅으로 넘어간 단계를 구분해야 "아무도 안 눌렀는데 왜 제작 완료지?"에 답할 수 있습니다.
- **단계마다 메모**를 남길 수 있습니다. 왜 그렇게 처리했는지는 다음 사람이 알아야 하고, 이력과 CSV에 함께 실립니다.
- 버튼으로 상태를 넘기면 **진행 이력이 즉시 갱신**됩니다.

**제작처 연동 섹션**

- 사양 검증 결과(판형·주문 시 분량 vs 현재 분량)와 **제작처 이벤트 수신 이력**을 함께 봅니다.
- 주문 상태와 발주 여부에 따라 **안내 문구가 달라집니다** — 아직 확인 전이면 발주할 수 없다고, 확인됐고 사양이 통과면 발주할 수 있다고, 취소된 건이면 아무 안내도 띄우지 않습니다.
- 확인 후 발주해야 제작이 시작되는 구조라, **`주문 확인`을 누르면 발주 모달이 이어서 열립니다.** 거기서 바로 발주하지 않아도 상세 페이지의 연동 섹션이 하이라이트로 남아 "아직 발주 안 됨"을 알립니다.

**회원·모임 관리**

- 목록에 필터를 두고(이름·ID·모임명 통합 검색, 가입 기간 / 모임명·개설 기간), 회원 상세에서 **가입한 모임**으로, 모임 상세에서 **가입 회원**으로 바로 이동합니다.
- 회원·모임 단위로도 **운영자 메모**를 남길 수 있습니다.

### 공통 동작

**되돌릴 수 없는 동작에는 확인을 한 단계 둡니다.** 잘못 누른 한 번으로 사라지면 안 되는 것들입니다.

- 코멘트·답글 삭제, 책 삭제 — 소프트 딜리트라 데이터는 남지만 화면에서는 사라집니다.
- 주문 취소·구매 확정·환불 요청·재제작 요청 — 상태가 종결되거나 되돌릴 수 없는 분기로 갑니다.
- 운영자의 단계 진행·일괄 처리·제작처 발주 — 발주는 실제로 제작이 시작되는 지점입니다.
- 확인 모달의 문구는 **무엇이 일어나는지**를 씁니다. "정말 삭제하시겠습니까?"가 아니라 "문집을 잘 받으셨나요? 구매를 확정하면 주문이 마무리돼요"처럼, 누르면 무엇이 끝나는지 알 수 있게.

**동작이 끝나면 토스트로 알립니다.** 화면이 조용히 바뀌면 됐는지 안 됐는지 알 수 없습니다.

- 위치는 **화면 하단 중앙**입니다. 상단은 GNB와 겹치고, 모바일에서는 엄지가 닿는 쪽이 아래입니다.
- 안내가 연달아 뜰 때 **덮어쓰지 않고 위로 쌓입니다.** 새 토스트가 아래에 붙고 이전 것이 밀려 올라가, 방금 무슨 일이 있었는지 순서대로 읽힙니다.
- 같은 메시지가 아직 떠 있으면 다시 쌓지 않습니다 — 가드가 두 번 도는 경우 같은 안내가 겹쳐 보이던 것을 막습니다.
- 3초 뒤 자동으로 닫히고, 급하면 직접 닫을 수 있습니다.

- 로그아웃하면 세션·캐시·저장소를 전부 비웁니다. 다시 로그인했을 때 앞사람의 필터가 남아 있지 않도록.

### 정상 경로를 벗어났을 때

- **로딩** — 영역 단위 스켈레톤. 책방에서 필터를 바꾸면 책장만 스켈레톤이 되고 히어로(지금 읽는 책)는 유지됩니다. 한 영역의 실패가 다른 영역을 죽이지 않습니다.
- **빈 목록** — 다음 행동까지 씁니다. 필터가 있는 목록은 **'조건에 맞는 것이 없음'과 '아직 하나도 없음'을 구분**합니다.
- **조회 실패** — 에러 뷰 + 재시도.
- **없는 경로 vs 없는 대상** — 갈래를 나눴습니다.
  - `/nope` 처럼 경로 자체가 없으면 → 공통 404 (GNB·푸터 유지, 로그인 상태에 따라 돌아갈 곳이 달라집니다).
  - `/books/틀린id` 처럼 경로는 맞고 대상이 없으면 → **"책 정보를 찾을 수 없어요"** + 책방으로. **'다시 시도'를 감춥니다** — 404에 재시도를 권하면 영원히 실패하는 버튼이 됩니다.
- **입력 검증** — 필드별로 무엇이 왜 잘못됐는지 쓰고, **고치기 시작하면 즉시 에러를 거둡니다**. 여러 칸이 함께 틀린 경우(함께 읽기 시작·끝)는 두 칸을 붉게 표시하고 문구는 아래 한 줄로 모읍니다.
- **에러 계약** — 서버 에러는 전부 `{ code, message }` 형태이고 **한글 카피는 백엔드 enum 한 곳에서만** 관리합니다. 프론트에 별도 한글 맵을 두면 두 벌이 어긋납니다.
- **문집 진입 가드** — 완독한 책이 없으면 **고를 것이 하나도 없는 주문서로 보내지 않고** 이유를 먼저 알립니다. 분량이 최소 쪽수에 못 미치면 **다음 단계로 넘어가기 전에** 막습니다.

### 화면 크기가 달라도

**모든 화면을 데스크톱·모바일 반응형으로 만들었습니다.** §1의 페르소나별 기기(토론=모바일, 관리=데스크톱)는 *어디서 주로 쓸지에 대한 가정*이지, 그 기능을 그 기기에서만 쓸 수 있다는 뜻이 아닙니다. 문집 주문서도 모바일에서 4단계를 끝까지 진행할 수 있고, 운영자 화면도 모바일에서 열립니다.

그 위에서 내린 판단들입니다.

- **운영자 테이블은 좁은 화면에서도 카드로 바꾸지 않았습니다.** 카드로 접으면 컬럼 간 비교가 불가능해지고 렌더 경로도 두 벌이 됩니다. 운영자에게는 주문일시·상태·최근 변경을 나란히 놓고 보는 것 자체가 정보라, **테이블을 유지하고 자기 영역 안에서만 가로 스크롤**하게 했습니다.
- **좁은 화면에서는 레이아웃 자체를 다르게** 뒀습니다. 데스크톱에서 가로로 놓던 것을 세로로 접습니다 — 책 등록 모달의 표지 팔레트와 날짜 3칸, 문집 주문서의 담은 책 패널(옆 → 하단 고정)이 그렇습니다. 그대로 두면 모달 안에 가로 스크롤이 생기거나 라벨이 잘립니다.
- **여백이 과하게 좁혀지지 않게** 했습니다. 폭이 줄었다고 콘텐츠를 화면 끝까지 붙이면 읽기 어려워, 좌우 패딩은 고정값으로 유지하고 안쪽 콘텐츠만 줄어들게 했습니다.
- 문집 주문서처럼 **하단에 버튼이 고정된 화면**은 그 영역 높이만큼 본문 아래 여백을 확보했습니다. 안 그러면 마지막 항목이 버튼에 가려 보이지 않습니다.
- **실기기(iOS 사파리·크롬)에서 확인**했습니다. 데스크톱 개발 중에는 보이지 않던 **하이드레이션 에러**가 여기서 드러났습니다 — 브라우저 확장이 `<html>`에 속성을 주입하거나, iOS 사파리가 전화번호·날짜처럼 보이는 문자열을 자동 링크로 바꾸면서 서버 HTML과 어긋나던 건입니다.

### 화면이 흔들리거나 어긋나 보이던 것

기능이 없어서가 아니라 **있는데 읽기 불편해서** 손댄 것들입니다.

- 창 너비를 줄일 때 레이아웃이 진동하던 것 — 스크롤바가 나타났다 사라지며 줄바꿈 판정이 뒤집혔습니다 (`scrollbar-gutter: stable`).
- 모달·드롭다운을 열면 화면이 왼쪽으로 밀리던 것 — 스크롤바 자리를 이미 잡아 뒀는데 MUI가 같은 폭만큼 보정을 또 넣고 있었습니다.
- 책 제목이 두 줄이 되면 그리드 행이 어긋나던 것.
- 코멘트끼리 경계가 흐려 한 사람의 말이 어디서 끝나는지 헷갈리던 것 (구분선·인용구 배경 대비).
- 툴팁이 대상에서 멀리 떨어져 어디에 대한 설명인지 흐리던 것.

### 불필요한 호출과 로딩 덜어내기

- **주문 1단계에서 책을 한 권 선택할 때마다 견적 요청 API가 호출되고 있었습니다.** 견적이 실제로 필요한 건 판형을 고르는 3단계라, 그 단계에 들어갈 때 한 번만 호출하도록 정리했습니다.
- **로그인 모달과 멤버 메뉴는 눌러야 열리는데도 모든 페이지가 그 코드를 미리 받고 있었습니다.** 모달을 열 때 받도록 미뤄 첫 로드에서 덜어냈습니다 (랜딩 기준 306→285KB, gzip).
- 목록은 페이지네이션이 기본이고, 서버 상태는 TanStack Query가 캐싱합니다 — 화면을 오갈 때마다 같은 요청이 반복되지 않습니다.

### 의도적으로 넣지 않은 것

**과제 범위 밖이라 뺀 것** — 안내문이 "결제·배송·회원 인증은 구현 대상이 아닙니다"라고 명시한 항목들입니다.

| 안 넣은 것             | 대신 한 것                                                                                               |
| ---------------------- | -------------------------------------------------------------------------------------------------------- |
| 회원 인증(가입·로그인) | 회원제 서비스가 맞지만 인증 대신 콘텐츠 기능에 집중하고, 계정 선택 로그인 방식으로 회원 관점은 유지 (§3) |
| 결제·정산              | 견적 **금액은 계산해서 보여주되** 결제 수단은 없습니다. 주문은 "접수"까지                                |
| 주소 입력·택배사 연동  | 배송은 **상태와 송장번호 표시**로만. 제작처가 주는 값을 받아 보여줍니다                                  |

**만들지 않기로 판단한 것** — 이쪽이 실제 설계 판단입니다.

| 안 넣은 것                     | 이유                                                                                                                                                                                                                                               |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 단순 변심 환불·교환            | 문집은 **주문 제작 상품**이라 재고가 없습니다. 교환할 다른 물건이 없으니 구제책은 재제작이고, 청약철회도 제한 대상입니다. 그래서 **하자가 있을 때만** 환불·재제작을 받고, 그 사실을 확인 모달 문구에 그대로 씁니다                                 |
| 책 상태 자동 전환              | 기간이 시작돼도 '읽는 중'으로 자동으로 바뀌지 않습니다. **날짜는 계획, 상태는 실제 진행**이라 독서모임처럼 일정이 변동될 수 있는 곳에서는 시스템이 바꿔 둔 값을 모임장이 다시 되돌리는 일이 반복됩니다.                                            |
| 알림·실시간(웹소켓)            | **실시간성이 낮은 것이 이 서비스의 성격**입니다(§7). 같은 책을 읽고 각자 속도로 남긴 기록이 모여 토론이 되는 구조라, 코멘트 기간도 정해두지 않았습니다 — 한 문장씩 붙는 기록에 실시간 연결은 과합니다. 대신 토론 조회만 창 복귀 시 다시 불러옵니다 |
| 회원 정지 등 상태 변경         | 비즈니스 로직은 **문집 주문 하나에 집중**했습니다. 운영자에게 회원·모임은 주문을 이해하기 위한 맥락이라, 조회와 운영자 메모까지만 뒀습니다                                                                                                         |
| 외부 도서 검색 API             | 외부 의존 배제 요건 때문이기도 하지만, **색 + 이모지로 직접 고르는 표지**가 '우리 모임 책방'이라는 성격에 더 맞습니다. 같은 책이라도 모임마다 다른 표지가 됩니다                                                                                   |
| 레이플랫 판형·템플릿 제작 방식 | 사진 중심 사양이라 텍스트 문집에 맞지 않고, 내지 PDF가 펼침면이라 조판을 따로 만들어야 합니다. **제작 방식을 하나(`PDF_UPLOAD`)로 고정**해 검증 경로를 단순하게 유지했습니다                                                                       |

## 5. 기술 스택 및 아키텍처

### 스택

| 영역     | 기술                                                                     |
| -------- | ------------------------------------------------------------------------ |
| Frontend | Next.js 16 (App Router), TypeScript, TanStack Query, Zustand, MUI, Axios |
| Backend  | NestJS 11, Prisma 6, PostgreSQL 16                                       |
| 실행     | Docker Compose (db · backend · frontend)                                 |

### 왜 이 스택인가

**TypeScript 단일 언어로 프론트–백–DB를 잇는, 현재 실무에서 매일 쓰는 조합입니다.** 제한된 기간에 학습 비용 없이 구현 완성도에 시간을 쓰기 위한 선택입니다.

- **서버 상태(TanStack Query)와 클라이언트 상태(Zustand)를 분리**했습니다. 캐싱·재검증이 필요한 것과 세션처럼 화면 밖에서도 읽어야 하는 것은 성격이 다릅니다.
- **API 타입은 코드 생성**입니다. 백엔드 DTO → `openapi.json` → 프론트 타입. 프-백 계약이 어긋나면 **빌드가 깨져서** 알려줍니다 (실제로 이 파이프라인이 오류를 잡아낸 사례가 §6에 있습니다).
- **UI는 MUI**를 씁니다. 실무에서 대부분의 프로젝트에 쓰고 있어 익숙하고, **스타일이 어느 정도 잡힌 컴포넌트를 적당히 커스텀해 쓰기 좋습니다.** 시간을 비주얼이 아니라 화면 판단(흐름·문구·상태 표시)에 쓰려는 선택이었고, 안내문도 기성 UI 사용을 권장합니다.

### 구조

```
bookclub-log/
├── docker-compose.yml      # db + backend + frontend
├── scripts/
│   └── regression-api.sh   # 도커 기동 후 서버 계약 44항목 검증
├── backend/
│   ├── prisma/schema/      # 도메인별 분리 (Club·Member·Book·Comment·Order)
│   └── src/
│       ├── apps/
│       │   ├── apis/       # 서비스 API (books·comments·orders·clubs·members)
│       │   └── admin/      # 운영자 API (orders·members·clubs)
│       └── shared/         # 두 앱이 공유 — bookprint·orders·constants·dto·filters·prisma
└── frontend/
    └── src/
        ├── app/            # 라우트 + 페이지 전용 컴포넌트(co-location)
        └── shared/         # api·components·constants·hooks·stores·styles·types·utils
```

#### ① 백엔드는 서비스와 운영자를 폴더로 갈랐습니다

`apps/apis`(서비스)와 `apps/admin`(운영자)을 나누고, 둘이 함께 쓰는 것만 `shared`에 뒀습니다. **한 DB를 공유하되 필요하면 서버를 분리할 수 있는 경계**입니다 — 서비스와 운영자는 트래픽 특성도, 권한 모델도, 배포 주기도 다릅니다. 지금 한 프로세스로 띄우더라도 경계는 미리 그어 두는 편이 낫습니다.

#### ② 프론트는 한 앱에 담았습니다 — 과제 단계의 선택입니다

원래는 **서비스 웹과 운영자 웹을 따로 두려고 했습니다.** 실제 서비스라면 도메인부터 다르고 배포도 따로 가는 것이 맞습니다.

그런데 이 과제는 심사자가 `docker compose up` 한 번으로 **서비스와 운영자 화면을 모두 확인**할 수 있어야 합니다. 앱을 둘로 나누면 컨테이너와 포트가 하나씩 더 늘고, 심사자가 두 주소를 오가야 합니다. 그래서 **하나의 웹에 `/admin` 경로로 운영자 화면을 두고, 세션을 배타적으로 분리**했습니다 — 회원 세션으로 `/admin`에 들어갈 수 없고, 운영자 세션으로 서비스 화면에 들어갈 수 없습니다. GNB도 서로 다른 메뉴로 바뀝니다.

운영자 기능도 같은 기준으로 좁혔습니다. 실제로는 운영자 계정도 **루트·직원 등 권한을 나누고** 그에 따라 메뉴와 액션을 제어해야 하지만, 과제 단계에서는 **주문 관리와 주문자·모임 조회를 확인할 수 있는 경로**를 만드는 데 집중했습니다. 운영자 인증도 두지 않고 로그인 모달의 탭으로 들어가게 했는데, 그 사실을 모달 문구에 그대로 밝혀 두었습니다.

백엔드를 미리 갈라 둔 것이 여기서 값을 합니다. 프론트를 나눌 때가 오면 **운영자 웹은 `apps/admin`만 보고, 서비스 웹은 `apps/apis`만 보면 됩니다.**

### 설계 규칙

**화면보다 공통 부품을 먼저 만들었습니다.** MUI를 화면에서 직접 쓰지 않고, 기존 프로젝트에서 하던 방식대로 한 겹 덮어 두고 시작했습니다.

1. **토큰** — 색은 `colors.ts`의 `colorChips`, 텍스트는 타이포 토큰(`text_{weight}_{size}`). 화면에서 임의의 hex나 폰트 크기를 쓰지 않습니다.
2. **테마** — MUI 테마 팔레트를 토큰에서 파생시켜, 기본 컴포넌트도 같은 색을 씁니다.
3. **공통 컴포넌트** — `Common*` 16종(`CommonButton`·`CommonInput`·`CommonModal`·`CommonTab`·`CommonPagination`·`Typo`·`VerticalGap`·`ErrorView`·`CommonEmptyState` 등).
4. **화면** — 이 컴포넌트만 조립합니다.

덕분에 문구·간격·색을 바꿀 때 **한 파일만 고치면 전 화면에 적용**됩니다. 실제로 '다시 시도' 버튼을 조건부로 감추거나(`ErrorView`), 확인 모달을 여러 곳에 붙이거나(`CommonConfirmModal`), 세로 여백 규칙을 바꿀 때(`VerticalGap`) 화면을 일일이 돌지 않았습니다.

**`shared/`는 프론트·백엔드 양쪽의 공용 자리입니다.** 규칙을 하나로 뒀습니다 — **서비스와 운영자가 함께 쓰거나, 전역으로 쓰이는 것만** `shared/`에 두고, 도메인 폴더에는 그 도메인 전용 코드만 남깁니다. 백엔드는 `apps/apis`·`apps/admin`이 함께 쓰는 것(전이 맵·북프린트 계약·에러 코드·Prisma)이, 프론트는 화면 전반이 쓰는 것(공통 컴포넌트·API 클라이언트·스토어·토큰)이 여기 들어갑니다.

**두 번 이상 반복되면 공통으로 올립니다.** 코멘트 앵커 표시가 토론과 마이페이지에 중복되자 `CommentAnchor`로, 빈 상태가 다섯 군데 생기자 `CommonEmptyState`로, 진행 이력이 주문자·운영자 양쪽에 필요해지자 하나의 컴포넌트에 `adminView` 플래그로 합쳤습니다. 같은 화면을 두 벌 유지하면 한쪽만 고치는 일이 반드시 생깁니다.

**프론트 API 타입은 직접 쓰지 않고 생성합니다.** 백엔드 DTO → Swagger(OpenAPI) → `openapi.json` → 프론트 타입. 손으로 선언한 타입은 서버가 바뀌어도 조용히 맞아 보이지만, 생성된 타입은 **빌드가 깨져서** 알려 줍니다. 사용처는 `shared/types/`의 도메인별 재노출 파일에서만 import하고, 생성 파일을 직접 참조하거나 화면에서 타입을 다시 선언하는 것은 금지했습니다.

- **API에 내부 id를 노출하지 않습니다.** 경로·응답 식별자는 `publicId`(cuid)만 씁니다. 정렬·조인 성능을 위한 int PK와 외부에 드러나는 식별자를 분리했습니다.
- **삭제는 소프트 딜리트가 기본**입니다. 답글이 달린 코멘트, 문집에 실린 책은 지워도 자리가 남아야 합니다.
- **목록은 페이지네이션이 기본**입니다(`page`/`limit` → `{ items, meta }`). 예외(한 화면에 전부 보여야 하는 유한 목록)는 컨트롤러 주석에 근거를 남깁니다.
- **에러 계약은 코드 enum 하나**입니다. 도메인 예외와 DTO 검증이 모두 코드를 던지고, 전역 필터가 한글 메시지를 붙입니다.

## 6. AI 도구 사용 내역

**Claude Code(Fable)를 개발 전 과정에 사용했습니다.** 런타임에는 AI가 들어가지 않습니다.

### 활용 방법

**0. 권한 경계부터 정했습니다.** DB 명령·커밋·푸시는 자동 실행되지 않고 반드시 확인을 거치도록 설정했습니다. 모든 커밋은 제가 변경 내용을 직접 확인하고 지시했을 때만 남습니다. DB 명령은 실제 서비스에서는 민감한 조작이라, 과제에서도 같은 기준으로 직접 실행하지 못하게 막아 두었습니다.

**1. 기획.** 이력서·포트폴리오와 과제 안내문을 함께 분석해 평가 포인트를 뽑고, 저의 특성과 과제를 잘 연결할 수 있는 주제 후보를 도출한 뒤 대화하며 기획 초안을 잡았습니다. 디테일한 부분을 이 단계에서 모두 정하지 않고, 메인 기능의 큰 틀만 잡고 시작했습니다.

**2. 도커·워크플로우 세팅.** 도커는 클로드가 먼저 세팅한 것을 제가 직접 실행해 검증했습니다. 구현에 들어가기 전에 문서 체계(PLAN·DECISIONS·HISTORY·TODO·AI_LOG)를 먼저 잡아 두었습니다 — 작업할 때마다 히스토리가 자동으로 남아 제가 일일이 기록하지 않아도 되고, 제출 전에 참고하기 좋은 형식으로 쌓이게 했습니다. `CLAUDE.md`에는 작업 도메인 → 읽을 문서 라우팅 표를 두어, 컨텍스트가 끊겨도 결정 근거가 이어지게 했습니다.

**3. 구현.** DB 설계부터 시작했고, 이 단계에서만은 모든 라인을 직접 보며 수정을 요청했습니다 — 스키마 파일의 도메인 단위 분리, 파일명을 모델명과 같은 파스칼 케이스(`Book.prisma`·`Order.prisma`)로 통일, 이넘·테이블 설명 주석 같은 것들입니다. 백엔드·프론트 첫 구현에서 폴더 구조와 아키텍처를 잡게 한 뒤로는, 클로드가 작성하는 코드를 기본적으로 최대한 유지했습니다 — 그래야 이후 클로드로 다시 수정하고 리팩토링하기가 쉽습니다. 저는 아키텍처가 무너진 곳이 없는지, 재사용될 부분이 잘 정리됐는지, 가독성이 떨어지지 않는지만 가볍게 보고, 실제 기능은 화면을 직접 써 보면서 QA했습니다. 화면을 쓰다가 단계별로 추가하면 좋을 버튼·플로우를 제시하며 기획을 디벨롭했고, 서비스 화면과 운영자 화면이 각각 끝났을 때를 큰 축으로 잡아 클로드에게 코드 리뷰를 시켜 리팩토링할 부분과 놓친 부분을 개선했습니다.

**4. 검증.** 주문 전이 맵은 유닛 테스트 24개로, 서버 계약은 도커 기동 후 44항목 회귀 스크립트(`scripts/regression-api.sh`)로 검증했습니다. 다른 폴더에 새로 클론해 `docker compose up --build` 한 번으로 뜨는지 심사자와 같은 경로로 확인했고, 재시작 시 시드가 중복되지 않는지·포트를 바꿔도 뜨는지까지 봤습니다. 모바일은 iOS 실기기(사파리·크롬)로 확인했고, 번들 크기와 라우트별 로드 비용은 빌드 산출물로 실측한 뒤 손봤습니다. 매 작업의 빠른 피드백은 타입체크·린트로 받되, 기능 단위가 끝날 때마다 프로덕션 빌드를 돌려 정적 검사가 못 잡는 문제를 걸렀습니다.

**5. 문서 작성.** 작업 과정에서 업데이트해 둔 문서들과 과제 안내문을 기반으로 클로드가 초안을 쓰고, 제가 하나하나 읽으면서 다시 발견한 빈틈들을 체크하고 업데이트했습니다. 이 README도 그렇게 만들어졌습니다.

`docs/DECISIONS.md`에 46개의 설계 판단을, `docs/AI_LOG.md`에 실패 사례를 남겼습니다. **AI가 틀린 것은 즉시 기록하는 규칙**을 뒀습니다.

### 실패·문제 사례 (전체는 `docs/AI_LOG.md`)

**1. 정적 검사를 통과했는데 프로덕션 빌드에서 터짐**

운영자 목록 필터를 URL 쿼리로 옮기며 `useSearchParams()`를 세 페이지에 도입했습니다. 매 작업마다 `tsc --noEmit`과 `eslint`로 검증했고 전부 통과했습니다. 그런데 제출 전 프로덕션 빌드를 돌리자 `useSearchParams() should be wrapped in a suspense boundary`로 **빌드 자체가 중단**됐습니다. 도커 실행이 이 빌드를 쓰므로 **그대로 제출했다면 심사자 환경에서 앱이 뜨지 않았을 것**입니다.

**2. 원인을 단정했다가 틀린 경우**

모바일에서 하이드레이션 경고가 떴을 때 AI가 `format-detection` 설정을 원인으로 지목했습니다. 설명이 그럴듯해서 그대로 수정했는데, 경고는 사라지지 않았습니다. 직접 서버 HTML과 브라우저 DOM을 대조해 보니 실제 원인은 **브라우저 확장이 `<html>`에 속성을 주입한 것**이었습니다.

**두 사례가 가리키는 결론은 같습니다.** AI가 실행한 것을 그대로 믿고 넘어가면 안 되고, **반드시 직접 실행해 화면을 써 보면서 문제가 없는지 확인**해야 합니다. 1번은 검사 도구가 전부 통과라고 말하는데도 실제 실행 경로에서 깨진 경우고, 2번은 AI의 진단이 그럴듯한데도 틀린 경우입니다 — 어느 쪽도 도구나 AI의 출력만 보고는 알 수 없었고, 직접 돌려 보고서야 드러났습니다.

그래서 AI에게 먼저 진단과 구현을 받더라도, **실제 코드를 열어 확인하고 결과를 검토해서 다른 허점은 없는지 직접 살피는 과정**을 습관으로 뒀습니다. 이 검토에서 AI가 놓친 것을 여러 번 잡았고(제작처 웹훅 전이가 이력에 '주문자'로 표시되던 버그, 시드 메모가 실제 역할과 어긋난 것 등), 그때마다 결과물은 더 견고해졌습니다. AI를 쓰는 속도의 이점은 유지하되, **믿는 지점을 출력이 아니라 검증에 두는 것** — 이전부터 AI를 활용하며 느껴 온 원칙인데, 이번 과제에서 그 중요성을 다시 한번 확인했습니다.

## 7. 설계 의도

### 왜 이 아이디어인가

과제 안내문의 예시 중 '독서 노트'에서 힌트를 얻었습니다. 마침 사서인 지인이 오픈채팅으로 온라인 독서모임을 운영하는 것을 지켜보던 참이었습니다.

그 모임은 날짜와 시간을 정해 두고 채팅방에 모여 함께 이야기하는 방식이었습니다. 실시간 대화 자체는 잘 굴러갑니다. 문제는 기록이었습니다 — 모임이 거듭될수록 여러 권의 책 이야기가 한 스크롤 위에 계속 쌓여, 언제 어떤 책을 읽었는지 다시 찾아보기 어렵습니다. 대화 중에 여러 이야기가 동시에 오가면 순서가 엉키며, 지나고 나면 어떤 책의 어떤 대목에 대한 말이었는지 알 수 없게 됩니다. 좋은 감상이 분명 오갔는데도 모임에 남는 형태가 없었습니다. 그래서 **오픈채팅보다 독서모임의 기록을 더 잘 남길 수 있는 서비스** — 책을 축으로 이야기가 모이고 남는 자리 — 를 만들자고 생각했고, 이렇게 쌓인 토론이라면 문집으로 묶어 실물 책으로 만들 수 있겠다고 봤습니다. 책을 좋아하는 사람들의 모임이니 더 어울리는 결말입니다.

**실시간성이 낮은 것은 이 서비스의 결함이 아니라 성격입니다.** 같은 책을 읽고 소감을 나누는 데 꼭 같은 시간에 접속해야 할 이유는 없습니다. 요즘은 시간을 맞추는 것부터가 일이라, 각자 자기 속도로 읽고 남긴 것이 모여 토론이 되는 편이 오히려 현실적입니다. SNS에서 종종 보이는 **교환독서** — 책을 주고받으며 서로가 남긴 밑줄과 메모를 읽는 — 를 온라인으로 옮긴 모습에 가깝습니다.

그래서 **코멘트를 남기는 기간을 따로 정해두지 않았습니다.** 읽기 전에는 기대를, 읽는 도중에는 밑줄과 인상 깊은 문장을, 다 읽고 나서는 정리된 생각을 남깁니다(입력창 문구도 그에 맞춰 달라집니다). 함께 읽는 기간이 지난 뒤에도 막지 않습니다 — 책에 적는 기간과 모임일은 "언제쯤 같이 읽었는지"를 남기는 기록이지 코멘트를 잠그는 장치가 아닙니다.

**과제 조건과도 맞았습니다.** 안내문은 "인쇄 API를 활용할 법한 콘텐츠 서비스"를 요구하면서 **콘텐츠가 본체여야 한다**는 조건을 달았습니다. 독서모임이 이 조건에 잘 맞는 이유는 **콘텐츠와 인쇄가 억지로 붙지 않기 때문**입니다. 모임의 토론은 그 자체로 가치가 있어서 문집이 없어도 서비스가 성립합니다. 동시에 그 기록은 이미 '책의 형태'를 하고 있어서 — 책 단위로 묶이고, 인용이 있고, 사람들의 목소리가 섞여 있어서 — 실물 책으로 만드는 것이 가장 자연스러운 종착지입니다.

그래서 **문집 만들기는 서비스의 입구가 아니라 출구**에 뒀습니다. 완독한 책이 없으면 진입할 수 없고, 코멘트가 쌓이지 않으면 최소 쪽수를 채우지 못합니다. **콘텐츠를 쌓는 것이 곧 문집을 만들 수 있게 되는 과정**입니다.

### 사업적 가능성

- **책을 읽는 사람이 늘고 있습니다.** 최근 '텍스트힙'이라는 키워드가 떠오르고 도서전이 해마다 흥행하는 등, 독서가 취향이자 문화로 소비되는 추세입니다. 그리고 책을 읽을수록 그 소감을 나누고 싶어지고, 읽은 기록을 남기고 공유하고 싶어진다고 생각합니다 — SNS의 독서 인증과 교환독서가 그 욕구를 보여줍니다. 이 흐름을 받아 줄 **사용성과 기능을 잘 만들면 충분히 가능성이 있다**고 봅니다.
- **재구매 주기가 콘텐츠에 내장돼 있습니다.** 월 1권씩 읽는 모임은 반기·연 단위로 문집을 만들 이유가 자연스럽게 생깁니다. 마케팅으로 만들어내는 수요가 아니라 **콘텐츠가 쌓이면서 발생하는 수요**입니다.

### 더 시간이 있었다면

- **커뮤니티** — 모임 밖 회원들이 소통하는 공간. 다른 모임의 책 후기, 모임 진행 노하우 공유, 원하는 모임 찾기 등 가능. 지금은 모임 안에 갇혀 있는 콘텐츠를 서비스 전체의 자산으로 만드는 방향.
- **모임 만들기·초대·가입 정식 플로우** — 지금 모임은 시드로만 존재합니다(초대코드 필드는 스키마에 잡아 뒀습니다). **모임 정원**도 여기 함께 붙습니다 — 멤버가 늘어나는 경로가 없는 지금 넣으면 아무도 검사하지 않는 컬럼이 되고, 정원의 실질 상한은 **문집 한 권에 담기는 분량**(부수 상한 100부·판형 페이지 상한)이 정한다고 봅니다(`docs/DECISIONS.md` D-044).
- **개인 기록과 개인 문집** — 모임 밖에서 개인적으로 읽은 책도 기록을 남기고, 여러 모임에서 읽은 책과 함께 **내 독서 전체를 한 권으로** 모을 수 있게 합니다. 모임 문집과는 성격이 다른 별개 상품입니다 — 모임 문집에는 다른 회원의 코멘트가 실리므로 모임 경계가 곧 콘텐츠 접근 경계이고, 개인 문집은 내 기록만 담습니다.
- **문집 구성 미리보기 고도화** — 지금은 쪽수와 표지만 보여주는데, 실제 내지 레이아웃을 미리 볼 수 있으면 주문 확신이 올라갑니다.
- **운영측의 이달의 추천책** — 매달 한 권을 골라 모임들에 제안합니다. 무엇을 읽을지 정하는 것이 모임장의 큰 일이라 이를 덜어 주고, 여러 모임이 같은 책을 읽으면 커뮤니티(모임 간 소통)로 이어질 소재도 생깁니다.
- **토론 알림** — 내 코멘트에 답글·공감이 달리거나 참여 중인 책에 새 코멘트가 쌓이면 알려 줍니다. 실시간 연결 없이 기록이 쌓이는 구조라, 다시 들어올 계기는 알림이 만들어 줘야 합니다.
- **표지 이미지 업로드·외부 도서 검색** — 지금은 색·이모지 조합으로 표지를 만듭니다. 외부 의존 없이 동작해야 하는 과제 조건에 맞춘 임시 방식이라, 실제 서비스라면 도서 검색으로 표지를 가져오는 쪽이 자연스럽습니다.
- **회원 탈퇴·모임 탈퇴** — 회원제 서비스라면 있어야 할 흐름이지만, 우선은 서비스의 콘텐츠 기능을 먼저 완성했습니다.
- **운영자 계정 구분과 CS 기능** — 지금 운영자 화면은 인증 없는 단일 진입입니다. 실제 운영이라면 루트·직원 등 **권한을 나누고**, 환불·재제작 요청에 대한 **문의 응대(CS) 흐름** — 문의 접수·답변·처리 이력 — 이 붙어야 합니다. 운영자 메모는 그 첫 조각입니다.
